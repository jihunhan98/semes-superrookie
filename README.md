## 1. 요구사항 추가·변경 영향 알림

### 원하는 결과

요구사항이 추가되거나 변경되면 AI가 같은 프로젝트의 전체 요구사항을 검토하고, 영향을 받는 요구사항 ID·현재 구절·변경 전후 값·영향 이유를 알려줍니다.

예시 데이터이며 실제 확정 정책은 아닙니다.

| 항목 | 표시 예시 |
|---|---|
| 변경 원인 | REQ-AMR-001: 작업 배정 최소 SOC 50% → 30% |
| 영향 대상 | REQ-AMR-008: 후보 필터 조건 |
| 영향받는 현재 내용 | “SOC 50% 이상인 AMR을 후보로 선정한다.” |
| AI 영향 이유 | 배정 기준은 30%로 낮아졌지만 후보 선정은 50%로 남아 있어, SOC 30% 이상 50% 미만의 AMR이 배정 후보에서 제외됩니다. |
| 제안 | 후보 조건의 50%를 30%로 맞추는 수정안 검토 |
| 추가 확인 | 충전 복귀 요구사항과의 관계도 검토. 같은 배터리 수치라도 의미가 다르면 일괄 치환하지 않음. |

표시 방식:

- 저장 후 “AI가 변경 영향을 확인하고 있어요” 상태를 표시합니다.
- 분석 완료 시 “영향받는 요구사항 3건” 알림을 표시하고 상세 목록으로 연결합니다.
- 일시적인 알림 외에 프로젝트 내 지속 조회 가능한 영향 목록과 미확인 건수를 제공합니다.
- 상세 카드에는 원인 요구사항 → 영향 대상, 원문 위치, 이전 값 → 변경 값, 이유, 대상 열기를 표시합니다.
- 신규 등록은 이전 값 없이 “추가된 조건”을 표시합니다. 아직 확정되지 않은 변경은 “예상 영향”으로 구분합니다.
- 알림을 읽었다는 상태와 요구사항 수정이 완료됐다는 상태는 별개입니다.
- AI 분석 실패·근거 부족·영향 없음은 구분합니다. 재시도 시 동일 변경 알림을 중복 생성하지 않습니다.

전체 요구사항 전문과 ID·상태·버전, 변경 전후 본문을 AI에 전달합니다. 분석 도중 입력 버전이 바뀌면 결과를 만료 처리하고 재분석합니다. 모델 입력 한도를 초과하면 누락한 채 성공 처리하지 않고 실패 사유를 안내합니다.

관련 개발 작업: 기존 `MON-01`~`MON-03`, `MON-07`~`MON-09`를 활용하고 알림 UI·읽음 상태를 연결합니다.

## 2. 실제 클래스명 기반 시퀀스·클래스 다이어그램

### 현재 코드에서 확인한 문제

확인 기준: 문서 작성 직전 `semes` 커밋 `557b8b83d921b740559554c0ef19fd37654c454e`.

- [ai-model/main.py](ai-model/main.py)의 `_DETAIL_DESIGN_PROMPT`는 업무 개념과 업무 언어를 쓰도록 지시합니다. 실제 구현 클래스 구조를 보고 싶은 요청과 방향이 다릅니다.
- `_ask_llm_artifact`는 이슈 제목·근거 구절·대상 요구사항 전문·다른 요구사항 전문·재생성 지시를 전달하지만, 실제 VCS 클래스·메서드·호출 관계 목록은 전달하지 않습니다.
- [ai-model/artifacts.py](ai-model/artifacts.py)의 `generate_v2`에는 업무 개념 기반 기본 다이어그램이 있습니다. 이 결과를 실제 구현 구조로 해석해서는 안 됩니다.
- [ProjectKnowledgeService](backend/src/main/java/com/semes/reqops/domain/knowledge/service/ProjectKnowledgeService.java)는 출처 버전별 내용을 저장하는 기반입니다. 이 클래스의 존재만으로 실제 VCS 소스의 클래스 색인과 AI 연결이 완료됐다고 볼 수 없습니다.

### 해결 방안

**요구사항 관리 도구인 ReqOps의 클래스가 아니라, 분석 대상인 실제 VCS/장비 SW의 코드 근거를 AI에 제공해야 합니다.** 클래스 이름 목록만으로 실제 실행 순서까지 확인할 수는 없으므로 메서드 본문·호출 관계도 필요합니다.

1. 프로젝트에 대상 소스 스냅샷 또는 구조화된 클래스 명세를 등록합니다. 초기에는 폐쇄망에서 추출한 자료 업로드 방식도 지원하도록 설계합니다.
2. 언어에 맞는 파서로 namespace/package, 클래스, 메서드 시그니처, 필드, 상속·의존·호출 관계를 추출합니다. 단순 정규식만으로 모든 언어를 처리한다고 가정하지 않습니다.
3. 각 항목에 파일 경로, 소스 위치, 소스 버전/커밋, 심볼 ID를 연결합니다.
4. AI가 전체 요구사항과 관련 코드 근거를 함께 보고 요구사항 ↔ 클래스·메서드 연결을 도출합니다. 관련 코드 검색은 가능하지만 전체 요구사항 전문 포함 원칙은 유지합니다.
5. AS-IS는 기존 코드로 확인된 관계를, TO-BE는 요구사항 반영을 위한 변경 제안을 표현합니다.
6. 생성된 클래스·메서드가 제공한 코드 목록에 있는지 검증하고 Mermaid 렌더링까지 확인합니다.

| 다이어그램 | 표시 내용 |
|---|---|
| 클래스 | 실제 클래스명, 관련 필드·메서드, 상속·의존 관계, 변경 대상과 변경 이유 |
| AS-IS 시퀀스 | 실제 클래스/객체를 참여자로 사용, 메서드 호출·조건 분기·반환과 근거 위치 |
| TO-BE 시퀀스 | 같은 클래스명으로 변경 후 조건·호출 흐름을 제안하고 변경 부분 표시 |
| 근거 패널 | 요구사항 ID·버전, 코드 파일·심볼·소스 버전, 확인되지 않은 관계 |

등록되지 않은 클래스명을 실제 존재하는 것처럼 생성하지 않습니다. 새 클래스가 필요하면 “신규 클래스 제안”으로 분리합니다. 코드가 없으면 실제 코드 기반 다이어그램을 생성할 수 없다는 상태와 필요한 자료를 표시합니다. 이벤트·콜백·동적 바인딩처럼 정적 분석만으로 순서를 확정할 수 없는 부분은 미확인으로 남기고, 제공된 명세나 실행 추적으로 보완합니다.

### 개발 이슈와 완료 기준 — 구현 반영

| ID | 개발 내용 | 완료 기준 |
|---|---|---|
| DIAG-001 | 대상 코드·클래스 명세 등록 및 버전 관리 | 대상 프로젝트와 소스 버전을 식별하고 출처를 조회할 수 있음 |
| DIAG-002 | 클래스·메서드·호출 관계 색인 | 심볼을 파일·소스 위치에 연결하고 미확인 관계를 구분 |
| DIAG-003 | 요구사항-코드 매핑 및 생성 프롬프트 개선 | 전체 요구사항 + 코드 근거로 실제 클래스명 사용, AS-IS/TO-BE 구분 |
| DIAG-004 | 심볼·관계·Mermaid 검증과 근거 표시 | 존재하지 않는 기존 클래스를 차단하고 렌더링 오류·근거 부족을 노출 |

## 3. 개발 이슈·산출물 도출 정확도 개선

### 현재 코드에서 확인한 문제

- `_SPLIT_SYSTEM_PROMPT` 및 `_ask_llm_split`의 분할 결과는 주로 제목과 원문 구절입니다. 원문 구절 존재 검증은 있지만, 이슈 전체가 모든 조건·예외를 빠짐없이 덮었는지를 보장하는 검증은 별도로 필요합니다.
- `is_valid_v2_shape`는 필수 키와 시나리오 종류 등 구조를 확인합니다. SOC 값·비교 연산자·단위의 일치, 요구사항 누락, 실제 클래스 근거 같은 내용 정확성을 충분히 확인하지 않습니다.
- `_ask_llm_artifact`는 이슈의 제목과 구절을 받습니다. 개발 이슈 본문의 변경 범위·제약·전후 상태를 산출물에 일관되게 반영하도록 입력 계약을 보강해야 합니다.
- 기존 `DevIssue`에는 `id`, `issueKey`, `displayOrder`가 존재합니다. 화면 순번과 식별자를 구분하고 이슈 재생성·분할·병합 시 연결 이력을 보존해야 합니다.

### 개선 처리 흐름

1. AI가 요구사항을 조건, 대상, 동작, 수치·단위·비교 연산자, 우선순위, 예외, 확인 필요 항목으로 구조화합니다. 각 항목은 원문과 버전에 연결합니다.
2. AI가 구현 가능한 단위로 개발 이슈를 도출합니다. 제목·원문 외에 목적, 변경 범위, 변경 전후, 제약, 완료 기준, 관련 요구사항을 채웁니다. 근거 없는 정책·수치는 만들어 넣지 않습니다.
3. 구조화한 항목마다 담당 개발 이슈를 연결합니다. 미연결 항목은 누락 후보로, 중복 연결은 의도적인 공유인지 AI가 검토합니다.
4. 개발 이슈 본문과 근거를 공통 입력으로 산출물 4종을 생성합니다. 각 산출물의 필드/시나리오에도 근거 항목을 연결합니다.
5. AI가 전체 요구사항, 개발 이슈, 산출물 묶음을 다시 검토해 누락·상충·수치 불일치를 찾고 수정안을 생성합니다. 형식·ID·근거 존재 여부는 프로그램으로도 검증합니다.
6. 필요한 정보가 없는 항목은 “확인 필요”와 이유로 남깁니다. 생성 실패를 정상 완성 문서로 표시하지 않습니다.

| 산출물 | 보강 기준 |
|---|---|
| 개발 이슈 본문 | 무엇을 왜 어디까지 변경하는지, 전후 상태, 제약, 완료 기준, 근거 ID |
| SWVOC | 실제 요청 취지·요청 내용·특이사항, 미확인 요청자 정보 구분 |
| 기능 요구사항 | 선행조건 → 동작 → 후행조건, 기본·변형·예외, 수치·단위·경계값 |
| 비기능 요구사항 | 확인된 성능·신뢰성 등 품질 기준과 검증 방법. 명시되지 않은 목표 수치는 확인 필요 |
| Detail Design | 실제 클래스·메서드, 변경 전후 흐름, 영향 위치와 근거. 2번 코드 정보와 연결 |

프로젝트 전체 요구사항 전문은 각 생성·검토 프롬프트에 포함합니다. 다른 요구사항의 관련 사실을 사용할 때 해당 ID·버전을 명시합니다. 분량 제한 때문에 일부를 조용히 제외하지 않습니다.

### 개발 이슈 표시 ID

화면의 “개발 이슈 1”을 **`DEV-000123 | SOC 후보 선정 기준 변경`**처럼 표시하는 방안을 제안합니다. ID 예시는 표시 규칙 제안이며 현재 발급된 이슈가 아닙니다.

- AI가 ID를 임의 생성하지 않고 저장된 고유 식별자를 기준으로 서버에서 발급합니다.
- 순서 변경, 제목 수정, 산출물 재생성으로 같은 이슈의 ID가 바뀌지 않습니다.
- 실제 분할·병합으로 새 이슈가 생기면 새 ID를 발급하고 이전 이슈와의 관계를 남깁니다.
- 기존 `issueKey` 기반 URL·근거 링크·저장 데이터는 호환성을 유지합니다. 기존 ID를 일괄 덮어쓰지 않습니다.
- 카드 제목, 상세 화면, 알림, 산출물 연결, 내보내기에서 동일 ID를 사용합니다.

### 개발 이슈와 완료 기준 — 구현 반영

| ID | 개발 내용 | 완료 기준 |
|---|---|---|
| ART-001 | 요구사항 원자 항목 구조화·근거 연결 | 조건·수치·예외 각각을 원문 ID·버전에 추적 가능 |
| ART-002 | 개발 이슈 본문·완료 기준 도출 및 누락 검토 | 요구사항 항목별 연결/미연결 이유를 표시 |
| ART-003 | 산출물 4종 입력·응답 계약 보강 | 이슈 본문과 공통 근거를 반영하고 필드별 근거 표시 |
| ART-004 | AI 교차 검토 및 의미 검증 | 수치·연산자·단위 불일치와 누락·상충을 검출 |
| ART-005 | 고정 개발 이슈 ID 표시와 이력 호환 | 목록·상세·알림에서 같은 ID, 재정렬 후 유지, 기존 링크 접근 가능 |

### 대표 검증 사례

- “SOC 50% 이상 → 30% 이상”에서 30% 미만/동일/초과의 기대 동작이 근거와 일치합니다.
- “이상”을 “초과”로 잘못 생성하거나 30%를 0.3%로 바꾸면 오류로 검출합니다.
- 기존 충전 조건이 별도 정책이면 무조건 30%로 바꾸지 않고 영향·상충 이유를 설명합니다.
- 원문에 명시된 예외가 개발 이슈나 기능 시나리오에서 빠지면 누락으로 표시합니다.
- 제공하지 않은 클래스·메서드·성능 목표를 확정 사실로 생성하지 않습니다.
- 요구사항/코드 버전이 변경되면 기존 산출물의 재검토 필요 여부를 표시합니다.

## 4. UI 통일 요청 범위

기존 개편 화면의 파란색 계열 강조색, 밝은 배경, 둥근 카드·입력창, 버튼과 여백 기준을 재사용합니다. 실제 수정 시 기존 공통 스타일을 확인해 맞춥니다.

| 대상 | 변경 방향 |
|---|---|
| signup | 기존 로그인·프로젝트 화면과 카드, 필드, 주 버튼 스타일 통일 |
| 새 요구사항 등록 | 메타 정보와 본문 입력을 정돈하고 둥근 입력 영역 적용, 등록 후 AI 검토 상태를 일관되게 표시 |
| 추가로 반영할 내용 | 제목 “AI에게 추가로 검토 요청”, placeholder “수정하거나 더 확인할 내용을 입력해 주세요”, 버튼 “AI 재검토” |
| 재검토 진행 | 버튼/상태 “AI가 다시 검토 중이에요”, 입력값 유지, 중복 제출 방지 |

긴 설명을 덧붙이기보다 제목과 버튼으로 동작을 알립니다. 키보드 포커스·필수 항목·오류 표시·작은 화면 사용성도 유지합니다.

관련 작업 ID: `UI-001` signup, `UI-002` 새 요구사항 등록, `UI-003` AI 재검토 입력.  
실제 UI 구현을 반영할 때는 소스와 `frontend/dist/standalone`을 함께 갱신해 기존 `run-all.bat` 실행 방식에서도 확인할 수 있도록 합니다.

## 구현 구성

- 1번: 요구사항 변경/추가 → AI 영향 분석 → 알림·영향 상세.
- 4번: signup·등록·AI 재검토 화면을 기존 디자인 기준으로 통일.
- 2번과 3번: 코드 근거 수집 → 이슈/산출물 계약 → 실제 클래스 다이어그램 → 누락·일관성 검증을 연결했습니다.
