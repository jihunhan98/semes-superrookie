요청의 핵심은 ‘Jira 연동’보다 ‘익숙한 작업 화면’입니다.

Jira 디자인 + 평소의 업무 양식 + 그림·표·시퀀스 다이어그램을 자체 화면에 적용할 수 있습니다. 실제 Jira 등록이나 원본 페이지 임베딩이 필수는 아닙니다. 아래 첫 부분은 그 디자인 방향을 보여주고, 두 번째 부분은 현재 개발 이슈 도출 코드가 실제로 하는 일을 설명합니다.

01

디자인은 익숙하게, 양식은 업무에 맞게

Jira 스타일을 준용하되 내용은 저장된 개발 이슈와 산출물로 구성합니다.

디자인 방향

Jira를 사용하는 느낌의 정보 구조

  • 프로젝트 → 요구사항 → 개발 이슈로 이어지는 탐색 경로
  • 이슈 키·제목·상태를 상단에 두는 일관된 헤더
  • 본문과 오른쪽 상세 정보의 명확한 분리
  • 문서 탭, 표준 라벨, 표·첨부·활동 영역의 익숙한 배치
업무 양식

눈에 익은 순서로 내용을 읽기

  • 현상 → 개선 요구 → 변경 범위 → 제약 조건
  • SWVOC → 기능 → 비기능 → 상세 설계의 4종 문서
  • 선행 조건·수행 흐름·완료 조건을 같은 순서로 표시
  • 그림과 표, 변경 전·후 시퀀스를 본문 안에서 확인
‘Jira처럼 보이는 것’과 ‘사내 양식이 정확히 일치하는 것’은 별도입니다. 아래는 현재 문서 필드와 익숙한 Jira 구성을 조합한 설계 예시입니다. 실제 사내 화면·템플릿 샘플을 확인해 완전히 동일하다고 검증한 화면은 아닙니다.

VCS는 IDLE 상태이며 SOC 기준을 만족하는 AMR 후보를 조회한다. 후보별 경로 거리를 계산하고, 최단 거리 우선으로 선택하되 동일 거리이면 SOC가 높은 AMR을 선택한다. VCS는 선택 결과와 선정 근거를 매칭 이력으로 기록한다.

03

지금 개발 이슈는 어떻게 선정하는가?

현재 코드에서 확인한 동작입니다. 제안이나 새 프롬프트가 아닙니다.

현재 구현

선정의 핵심 기준은 ‘서로 다른 기능·모듈로 개발할 수 있는가’입니다.

확정된 고객 요구사항 한 건을 구현 단위로 나누도록 요청합니다. 요구사항이 이미 작은 변경이면 하나의 이슈로 유지합니다. 현재 프롬프트가 별도의 점수표로 우선순위·난이도·공수를 계산해 선정하는 구조는 아닙니다.

1기능·모듈의 경계

서로 다른 기능이나 모듈로 나눠 개발할 수 있는 지점을 이슈 경계로 삼습니다.

2불필요한 세분화 금지

이미 하나의 작은 변경이면 이슈 하나로 둡니다. 정해진 개수를 채우지 않습니다.

3원문에 있는 근거

각 후보의 quote는 현재 확정 본문에 그대로 들어 있는 연속 구절이어야 합니다.

4간결한 제목

제목은 15자 내외로 쓰도록 지시합니다. 실제 길이를 강제하는 검증은 아닙니다.

전체 흐름

01확정 요구사항프로젝트 권한과
CONFIRMED 상태 확인
02이슈 후보 선정AI에 title·quote 요청
사용자가 분할·병합·수정
03상세 본문 보완선정 목록 확정 시
새 이슈의 본문 작성
04산출물 4종 생성확정된 개발 이슈별로
백그라운드 생성 작업

후보 미리보기는 저장하지 않습니다. 목록을 확정하는 요청 이후에 상세 본문 보완과 저장, 문서 생성이 이어집니다. 이 과정에서 실제 Jira 이슈를 생성하는 호출은 없습니다.

선정 요청에 들어가는 정보

입력현재 전달 방식주의할 점
분할 대상선택한 확정 요구사항 전문부분 문장만 잘라 요청하지 않습니다.
추가 지시사용자가 재분할 시 입력한 참고 지시값이 있을 때만 user 메시지에 덧붙입니다.
다른 요구사항같은 프로젝트의 다른 요구사항 ID·본문 전문현재 요구사항은 제외하며, 확정 상태만 필터링하는 경로는 아닙니다.
상태·버전이 경로에서는 명시적으로 전달하지 않음user 메시지에는 ‘미상 / 없음’으로 표시될 수 있습니다.
용어사전·실제 코드 구조현재 /split 요청에는 별도 필드가 없음실제 구현 클래스·모듈을 알고 나누는 저장소 분석 기능은 아닙니다.
SYSTEM MESSAGE실제 _SPLIT_SYSTEM_PROMPT 원문
당신은 반도체 장비 소프트웨어(VCS/AMR) 요구사항을 개발 이슈(Jira 티켓)로
나누는 전문가다. 주어진 확정 요구사항 본문을 실제 구현 단위로 몇 개의 개발 이슈로
나눌지 판단하라.

규칙:
- 이슈 경계는 "서로 다른 기능·모듈로 나눠 개발할 수 있는 지점"을 기준으로 삼는다.
- 요구사항이 이미 하나의 작은 변경이면 이슈 1개로 둔다. 억지로 쪼개지 않는다.
- quote는 반드시 원문에 그대로 등장하는 연속된 구절이어야 한다 — 지어내지 않는다.
- title은 15자 내외로 간결하게.

반드시 아래 JSON 형식으로만 답한다.
{"issues":[{"title":"이슈 제목","quote":"원문 그대로의 해당 구절"}]}
USER MESSAGE실제 조립 방식 · 내용은 자리표시자
요구사항: [현재 선택한 확정 요구사항 전문]
참고 지시: [사용자가 입력한 재분할 지시 — 입력이 있을 때만 포함]

같은 프로젝트의 다른 요구사항 전문(모두 검토하고 관련성·상충 여부를 판단):
- REQ-EXAMPLE-02 (상태=미상, 버전=없음): [다른 요구사항 전문]
- REQ-EXAMPLE-03 (상태=미상, 버전=없음): [다른 요구사항 전문]
…

시스템 메시지의 ‘Jira 티켓’은 개발 이슈의 개념을 설명하는 표현입니다. 해당 선정 요청이 실제 Jira에 이슈를 등록한다는 뜻은 아닙니다.

브라우저 → 백엔드 → AI 서버 → 모델의 요청 형식

브라우저 → 백엔드: 분할 미리보기에 사용자 ID와 참고 지시를 보냅니다. 백엔드가 DB에서 확정 본문과 같은 프로젝트의 다른 요구사항을 읽습니다.

백엔드 → AI 서버: 아래 구조로 POST /split을 호출합니다. 값은 설명용 자리표시자이며 실제 고객 데이터가 아닙니다.

{
  "content": "[선택한 확정 요구사항 전문]",
  "reason": "[선택 입력 · 없으면 null]",
  "existing": [
    {
      "reqKey": "REQ-EXAMPLE-02",
      "content": "[다른 요구사항 전문]",
      "state": null,
      "version": null
    }
  ]
}

AI 서버 → 사내 OpenAI 호환 모델: 다음처럼 system/user 메시지를 나누고 temperature: 0으로 보냅니다. 인증 값과 실제 모델 주소는 포함하지 않았습니다.

{
  "model": "[설정된 사내 모델]",
  "messages": [
    {
      "role": "system",
      "content": "[위의 실제 _SPLIT_SYSTEM_PROMPT 원문]"
    },
    {
      "role": "user",
      "content": "[현재 본문 + 참고 지시 + 다른 요구사항 전문]"
    }
  ],
  "temperature": 0
}

모델에서 요구하는 결과는 제목과 원문 구절 두 가지입니다.

{
  "issues": [
    {
      "title": "AMR 후보 선정",
      "quote": "[현재 확정 본문에 실제로 포함된 연속 구절]"
    }
  ]
}
현재 응답에는 ‘왜 이 이슈로 나눴는지’가 없습니다.
선정 이유, 대안, 난이도, 공수, 분할 완전성, 모듈 연결 정보는 이 응답 규격에 들어 있지 않습니다. 이 정보를 UI에 명확히 표시하려면 선정 단계의 응답 규격부터 확장해야 합니다.
04

응답을 어떻게 검증하고, 실패하면 어떻게 되는가?

설명 주석보다 실제 조건문을 기준으로 정리했습니다.

01
후보마다 title·quote가 비어 있지 않은지 확인합니다.

앞뒤 공백을 정리한 뒤, quote가 현재 분할 대상 본문에 정확히 포함되는지 검사합니다.

02
유효하지 않은 후보는 개별적으로 제외합니다.

유효한 후보가 하나 이상 남으면 그 모델 결과를 사용합니다. 한 후보의 원문 불일치 때문에 항상 모델 결과 전체를 버리는 코드는 아닙니다.

03
유효 후보가 없거나 모델 호출이 실패하면 규칙 결과를 사용합니다.

일반 문장 경계로 나누며, 특례에 해당하면 본문 전체를 이슈 하나로 묶습니다.

04
AI 서버 자체를 호출하지 못하면 백엔드가 전체 본문 한 건을 반환합니다.

제목은 ‘전체 요구사항’, quote는 본문 전체이며 engine은 unavailable입니다.

실제 규칙 기반 특례

AMR + 매칭·IDLE·SOC·맨해튼 중 하나가 있으면 전체를 한 건으로 묶습니다.

LLM이 아닌 규칙 경로에서는 본문을 대문자로 정규화한 뒤 AMR이 포함되고, 매칭 / IDLE / SOC / 맨해튼 중 하나가 함께 있으면 본문 전체를 한 후보로 만듭니다. 제목은 ‘AMR 후보 선정 및 매칭 우선순위’입니다.

이 규칙은 여러 기능이 섞여 있는지를 의미적으로 증명한 결과가 아닙니다. 이 특례에 해당하지 않으면 문장 경계로 나누며, 규칙 제목은 최대 앞부분 22자를 활용합니다. 앞의 ‘15자 내외’는 LLM 지시와 구분해야 합니다.

사용자가 목록을 확정할 때 추가로 확인하는 것

조건현재 처리
확정 요구사항인지확정되지 않은 요구사항은 이슈 분할 대상이 될 수 없습니다.
근거 구절이 원문에 존재하는지브라우저와 백엔드에서 다시 확인합니다.
정확히 같은 quote의 중복여러 이슈에 동일한 근거 구절을 중복 연결하면 차단합니다.
일부만 겹치는 quote / 본문 누락현재 단계에 전체 범위의 겹침·완전성을 검증하는 조건은 없습니다.
상세 본문 작성새 이슈의 현상·개선 요구·범위·제약·변경 전후를 별도 AI 요청으로 보완합니다. 이 요청은 선정한 후보를 합치거나 추가하는 단계가 아닙니다.
등록 검토와 개발 이슈 선정을 구분해야 합니다.

개발 이슈 선택 카드에서 선정 이유·근거 구절·구현 범위·연결 문서가 함께 보여야 합니다. 단순 제목 목록으로 끝내지 않는 방향입니다.

프롬프트 제안“이 구현 단위를 독립적으로 확인할 수 있는지”

예를 들어 후보 조회·거리 계산·우선순위 정렬이 하나의 매칭 동작이라면 함께 묶는 근거를 쓰고, 별도 관리 대상인 이력 기록을 나누었다면 그 이유를 써야 합니다.

이 문서의 시안·예시 분할은 디자인 설명입니다. 실제 사내 모델의 응답을 재현하거나, 기존 사내 Jira 양식을 정확히 확인한 결과로 표시하지 않았습니다.
