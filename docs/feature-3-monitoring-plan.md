# 기능 3 — 요구사항 변경 모니터링 개발 계획

작성일: 2026-10-07  
대상 저장소 / 브랜치: `jihunhan98/semes-superrookie` / `semes`  
문서 상태: 개발 범위 제안. 이 문서의 항목은 구현 완료를 의미하지 않는다.

## 1. 목표와 기준

**요구사항이 추가·변경되면 AI가 프로젝트 전체를 확인해서 어디를 왜 어떻게 수정해야 하는지 알려주고, 반영 완료까지 추적한다.**

기준 문서인 [DESIGN.md 5장](../DESIGN.md#5-핵심-기능-3--산출물-관리--추적성)은 기능 3을 산출물 관리·추적성으로 정의한다. 기존 범위는 요구사항과 산출물 연결, 변경 영향 분석, 진행상황 관리다. 이 문서는 이를 변경 모니터링 기능으로 구체화한다.

기존 [기능명세서](기능명세서.md)는 기능 번호와 일부 설명이 과거 기준이다. 이 문서에서 기능 3은 DESIGN의 세 번째 핵심 기능을 뜻하며, 사용자 작업 흐름의 3단계와는 구분한다.

최근 요청사항을 반영한 원칙:

- 변경 의미 판단, 영향 분석, 수정안 작성, 일관성 재검증은 AI가 수행한다.
- 프로젝트 전체 요구사항을 프롬프트에 포함한다. 관련 요구사항만 선별해 나머지를 누락하지 않는다.
- 직접 연결된 산출물뿐 아니라 다른 요구사항과 그 산출물에 미치는 영향도 찾는다.
- 기존 확정본과 이력을 보존하고 수정 결과는 새 버전으로 남긴다.
- 실제 고객 합의 기록이나 확인되지 않은 코드·정책·수치를 AI가 사실처럼 만들어 내지 않는다.

## 2. 개발할 기능

| ID | 기능 | 개발 내용 | 사용자에게 보여줄 결과 |
|---|---|---|---|
| MON-01 | 변경 감지 | 신규 등록, 본문 수정, 재확정, 삭제·폐기 시 분석 자동 실행 | 변경된 요구사항, 시각, 변경 유형 |
| MON-02 | 변경 내용 분석 | 이전·현재 버전 비교 및 AI 의미 분석 | 문구 수정 / 조건·동작·기준 변경과 요약 |
| MON-03 | 관련 요구사항 분석 | 전체 요구사항에서 영향, 상충, 중복, 누락 탐색 | 관련 REQ-ID, 영향 이유, 수정 필요 여부 |
| MON-04 | 이슈·산출물 영향 분석 | 기존 개발 이슈와 산출물 4종의 내용 검토 | 영향받는 문서와 구체적인 수정 위치 |
| MON-05 | 수정안 자동 생성 | 이슈 본문, 문서 필드, 다이어그램의 수정안 생성 | 변경 전/후, 수정 근거 |
| MON-06 | 반영 및 재검증 | 수정안을 새 버전으로 반영하고 AI 일관성 재검사 | 해결 항목과 남은 영향·충돌 |
| MON-07 | 조치 상태 관리 | 감지부터 재검증 완료까지 상태·이력 추적 | 미처리 항목, 실패 원인, 재시도 |
| MON-08 | 모니터링 대시보드 | 프로젝트의 변경·영향·조치 현황 집계 | 최근 변경, 영향받은 항목, 미해결 건수 |
| MON-09 | 연결 관계 조회 | 요구사항 ↔ 개발 이슈 ↔ 산출물의 양방향 조회 | 근거 요구사항, 연결된 산출물, 사용 버전 |

삭제·폐기 감지는 해당 동작이 제공되는 경우 연결한다. 버전과 분석 근거를 보존할 수 있도록 물리 삭제에 의존하지 않는다.

산출물 4종은 SWVOC, 기능 요구사항, 비기능 요구사항, Detail Design이다. 개발 이슈 본문도 영향 분석 대상에 포함한다.

## 3. 영향 분석 범위

다음 두 가지를 함께 수행해야 한다.

1. **직접 영향:** 바뀐 요구사항에서 도출한 이슈·산출물의 수정 필요 여부 확인.
2. **교차 영향:** 다른 요구사항과 그 산출물에 새롭게 생긴 충돌·누락·수정 필요 여부 확인.

기존 연결 정보는 분석 근거로 활용하되, 연결이 없다는 이유만으로 영향 없음으로 판단하지 않는다. 특히 신규 요구사항은 기존 연결이 없으므로 전체 요구사항·기존 산출물과의 관계를 AI가 찾아야 한다.

### 예시

REQ-01의 “배터리 20% 이상이면 작업 할당”이 “30% 이상”으로 변경된 경우:

| 확인 대상 | AI 결과 예시 |
|---|---|
| REQ-01 기능 요구사항 | 작업 할당 선행조건 20% → 30% 수정 |
| REQ-01 Detail Design | 후보 AMR 선정 조건과 시퀀스 수정 |
| REQ-02 충전 관련 요구사항 | 충전 복귀 기준과 작업 할당 기준의 충돌 여부 확인 |
| REQ-02 연결 산출물 | 기존 20% 기준이 남아 있는 문서와 수정 위치 안내 |
| 관련 없는 요구사항·산출물 | 근거를 바탕으로 영향 없음 판정 |

위 수치는 동작 설명용 예시이며 실제 프로젝트의 확정 정책이 아니다.

## 4. AI 입력과 출력

### 4.1 입력

| 입력 | 목적 |
|---|---|
| 변경 요구사항의 이전·현재 내용 | 무엇이 바뀌었는지 비교 |
| 변경 유형, 사유, 버전·revision | 분석 대상과 변경 맥락 식별 |
| 프로젝트 전체 요구사항 전문, ID, 상태, 버전 | 교차 영향·상충·일관성 분석 |
| 기존 개발 이슈와 산출물 내용 | 수정이 필요한 구체적인 위치 확인 |
| 요구사항↔이슈↔산출물 연결 및 근거 구절 | 판단 근거와 사용 버전 추적 |
| 기존 미해결 영향·조치 이력 | 중복 조치와 누락 방지 |

프로젝트 전체 요구사항은 각 분석 호출에 포함한다. 산출물이 많아 분할 호출하더라도 요구사항 전체 포함 원칙은 유지하고, 산출물 분석 대상의 누락 여부를 기록한다. 모델 입력 한도를 초과하면 일부 요구사항을 조용히 잘라 성공 처리하지 말고 분석 불가 사유를 표시한다.

요구사항만 전달해서는 기존 산출물의 오래된 내용을 비교할 수 없으므로 산출물 본문도 분석에 제공해야 한다. 미확정 변경안과 현재 유효 확정본은 구분해서 전달한다.

### 4.2 출력

| 항목 | 내용 |
|---|---|
| 변경 원인 | 변경을 유발한 요구사항 ID·버전·구절 |
| 영향 대상 | 요구사항 ID, 이슈 ID, 산출물 ID·종류 |
| 수정 위치 | 필드, 문장, 동작 정의 행, 다이어그램 부분 |
| 영향 이유 | 변경과 대상 사이의 관계 및 근거 |
| 수정안 | 기존 내용, 제안 내용, 수정 설명 |
| 판정 | 수정 필요 / 영향 없음 / 근거 부족 |
| 분석 기준 | 입력 버전·revision과 분석 시각 |

AI 미응답, 타임아웃, 응답 형식 오류는 '영향 없음'으로 처리하지 않는다. 분석 실패 상태와 재시도 기능을 제공한다.

실제 VCS 소스가 입력되지 않은 경우 문서에 근거한 모듈·설계 변경 제안까지만 제시한다. 실제 코드 파일이나 클래스의 수정 위치를 확인했다고 표시하지 않는다.

## 5. 처리 흐름과 상태

1. 요구사항의 추가·변경 이벤트와 이전·현재 스냅샷을 저장한다.
2. 전체 요구사항과 기존 이슈·산출물을 수집한다.
3. AI가 변경 의미와 직접·교차 영향을 분석한다.
4. 영향받는 항목마다 수정 위치·근거·수정안을 생성한다.
5. 모니터링 상세 화면에서 변경 전/후와 수정 대상을 보여준다.
6. 수정안을 새 작업 버전으로 반영하고 과거 확정본은 보존한다.
7. AI가 수정 후 전체 일관성을 재검증한다.
8. 미해결 항목이 없으면 해당 변경의 조치를 완료 처리한다.

기본 진행 상태: 감지 → 분석 중 → 수정 필요 → 반영 중 → 재검증 → 완료.

추가 상태:
- 분석 실패: 실패 원인 표시 및 재시도.
- 근거 부족: 부족한 정보 표시. 영향 없음으로 취급하지 않음.
- 결과 만료: 분석 중 요구사항·산출물 입력 버전이 바뀐 경우. 최신 버전으로 재분석.

같은 변경의 중복 실행으로 조치가 중복 생성되지 않도록 변경 ID와 입력 버전을 기준으로 관리한다. 미확정 변경의 영향은 '예상 영향'으로 구분하고, 확정 시 최신 버전을 기준으로 다시 검증한다.

자동 반영 범위와 실행 방식은 구현 상세 설계에서 확정한다. 수정안 생성과 재검증은 AI가 수행하며, 기존 고객 합의 기록을 AI가 임의로 생성하거나 대체하지 않는다.

## 6. 화면 구성

| 화면 | 주요 내용 |
|---|---|
| 모니터링 메인 | 최근 변경, 분석 진행 상태, 수정 필요 목록, 미해결 건수 |
| 변경 영향 상세 | 변경 전/후, 영향 대상, AI 판단 근거, 수정안, 반영·재시도 |
| 연결 관계 보기 | 요구사항↔개발 이슈↔산출물 연결 및 역방향 근거 조회 |

기존 사용자 흐름의 **등록 → 검출 수정·요구사항 확정 → 이슈·산출물 도출 → 검토·전체 확정** 4단계는 유지한다.

모니터링은 프로젝트 전체를 확인하는 별도 메뉴로 구성한다. 수정이 필요하면 해당 요구사항의 기존 작업 화면으로 연결하며, 다섯 번째 사용자 단계로 추가하지 않는다.

문서 반영 상태와 실제 개발 진행 상태는 구분한다. 문서가 확정되었다는 이유로 실제 소프트웨어 개발·배포가 완료되었다고 표시하지 않는다.

## 7. 데이터 및 구현 작업

아래는 구현 시 필요한 개념 목록이며, 기존 엔티티·테이블 재사용 여부와 최종 명칭은 실제 코드 확인 후 결정한다.

| 구분 | 필요한 작업 |
|---|---|
| 변경 이력 | 변경 ID, 요구사항 ID, 이전·현재 버전, 변경 종류·사유·시각 저장 |
| 분석 작업 | 입력 버전, 실행 상태, 실패 원인, 재시도, 처리 결과 저장 |
| 영향 항목 | 대상 ID, 수정 위치, 판정, 근거, 수정 전/후 저장 |
| 조치 이력 | 반영 버전, 상태 전이, 재검증 결과 저장 |
| 연결 정보 | 요구사항 버전↔이슈↔산출물 revision 및 근거 구절 연결 |
| AI 연계 | 변경 의미·영향 분석·수정안·재검증 프롬프트와 구조화 응답 계약 |
| API | 변경·분석 결과 조회, 재시도, 수정안 반영, 조치 상태 조회 |
| 프론트 | 모니터링 목록, 영향 상세, 비교 보기, 연결 관계, 실패·진행 표시 |

기존 요구사항 버전, 묶음(bundle), 이슈·산출물 revision, 근거 링크, 작업 관리 구조를 우선 재사용한다. 현재 모니터링 구현 완료 여부를 이 문서만으로 판단하지 않는다.

## 8. 개발 순서

| 순서 | 범위 | 완료 기준 |
|---|---|---|
| 1 | 변경 이력·버전 연결 | 추가·변경을 구분하고 이전·현재 근거를 보존 |
| 2 | AI 영향 분석 | 직접 연결과 다른 요구사항의 산출물까지 분석 |
| 3 | 수정 위치·수정안 표시 | 대상·위치·이유·변경 전/후를 화면에서 확인 |
| 4 | 반영·재검증 | 새 버전 반영 후 남은 충돌과 누락 재확인 |
| 5 | 대시보드·진행 관리 | 변경별 미해결·실패·완료 상태 집계 |

**첫 구현의 핵심 완료 기준:** 요구사항 하나를 변경했을 때 다른 요구사항의 산출물까지 수정 대상을 찾아, 근거와 수정안을 보여준다.

## 9. 필수 확인 시나리오

- 기존 요구사항 변경 시 직접 연결된 산출물의 수정 위치를 찾는다.
- 신규 요구사항 추가 시 기존 연결이 없어도 교차 영향을 찾는다.
- 단순 문구 수정에는 불필요한 의미 변경안을 만들지 않는다.
- 영향 없음과 근거 부족·AI 실패를 구분한다.
- 수정안 반영 후 이전 확정본과 근거 링크를 조회할 수 있다.
- 분석 중 입력이 바뀌면 오래된 결과를 자동 반영하지 않는다.
- 동일 변경 재시도로 중복 영향 항목이 생성되지 않는다.
- 전체 요구사항과 분석 대상 산출물의 누락 여부를 확인할 수 있다.
- 수정 후 AI 재검증으로 미해결 충돌·누락을 표시한다.
