## 2. 기능 2 — 요구사항 검토

범위: 요구사항을 등록하고 AI로 불명확·상충을 검토해 **고객 합의를 거쳐** 확정, 버전으로 관리.

| ID | 기능 | 설명 | 우선순위 | 상태 |
|---|---|---|---|---|
| FR-2-01 | 요구사항 등록 | 직접 입력(요구사항 ID·요청자 소속/이름·내용). 등록 시 **저장과 AI 초기 검토를 함께** 수행하고 그동안 로딩을 보여준다. 등록 직후 상태=접수 | P0 | ✅ 구현 |
| FR-2-02 | 요구사항 목록 | 분류 그룹 없이 플랫하게 표시. 요구사항 ID를 크게, 내용을 작게. 상태·검색·담당자 필터 | P0 | ✅ 구현 |
| FR-2-03 | 담당자 필터 | 프로젝트 멤버 전원을 **이름 칩**으로 표시. 여러 명 선택 시 OR, 아무도 선택 안 하면 전체 | P0 | ✅ 구현 |
| FR-2-04 | AI 자동 검토 | 모든 요구사항에 대해 등록 즉시 자동 실행. 불명확 7종 + 기존 요구사항 상충 검출 | P0 | ✅ 구현 |
| FR-2-05 | AI 제안 반영 | AI 검토 결과는 **읽기 전용**으로만 보여주고, 제안이 반영된 문장을 본문 칸에 **미리 채워** 준다. 사용자는 그 텍스트를 그대로 쓰거나 직접 고치거나 등록 원문으로 되돌린다 (항목별 "적용" 버튼 없음). 원문을 그대로 보여주고 지적된 구절에 **번호 붙은 형광펜**을 칠해, 같은 번호의 카드에서 왜 문제인지 설명한다 — 구절만 나열하면 원문 어디인지 사용자가 직접 찾아야 하므로 | P0 | ✅ 구현 |
| FR-2-06 | AI 재분석 | "↻ 다시 분석"으로 1단계에 입력한 내용을 참고해 다시 검토 요청 | P1 | ✅ 구현 |
| FR-2-07 | 요구사항 확정·수정 | 최초 확정과 그 이후 수정을 **화면 하나**로 처리한다. 등록 자체가 이미 "확정에 쓸 기준 본문"을 만드는 일이므로, 최초 확정도 재확정과 같은 절차(AI에게 물어보기 → AI 검토 → 고객 합의 → 확정)를 탄다. AI는 **바뀐 부분 + 1단계 입력 내용만** 검토(확정 전이면 등록 원문 대비, 확정 후면 확정본 대비 — 이미 합의된 나머지는 다시 안 본다). 확정에 실제로 필요한 근거는 3단계 합의 내용과 4단계 변경 사유 확인에 남는다 → 최초는 v1.0.0, 이후는 v1.0.x | P0 | ✅ 구현 |
| FR-2-08 | 고객 합의 기록 | 합의 방법·고객측 담당자·합의일·합의 내용을 기록. **이 기록 없이는 확정 불가** — AI 의견이 합리적이어도 그것만으로 확정할 수 없다 | P0 | ✅ 구현 |
| FR-2-10 | 버전 이력 | 확정마다 버전(Semver) 부여, 커밋형 이력·버전 diff | P0 | ✅ 구현 |
| FR-2-11 | 요구사항 항목 설정 | 프로젝트마다 고객 요구서 양식이 다르므로, 프로젝트별로 요구사항 항목(필드)을 구성 | P1 | ⬜ 미구현 |

**상태값**: 접수 → 검토 중 → 고객 합의 대기 → 확정 → (수정) 변경 중 → 재확정 · 보류.
전이 조건·보류를 쓰는 케이스 등 자세한 내용은 [`요구사항_상태_명세서.md`](요구사항_상태_명세서.md) 참고.

**왜 화면을 하나로 합쳤나** — 애초에 "새 요구사항을 등록한다"는 행위 자체가 이미
확정의 대상이 될 본문을 만드는 일이다. 그 뒤로 확정에 이르기까지 하는 일은 매번
"지금 있는 본문(등록 원문이든 확정본이든)을 왜·어떻게 바꾸는가"로 성격이 같다.
그래서 최초 확정을 별도 화면·별도 규칙(입력 없음·본문 전체 검토)으로 떼어두지 않고,
확정 이후의 수정과 똑같은 절차(AI에게 물어보기 → AI 검토 → 고객 합의 → 확정)로 통일했다.

**AI 검출 유형(8종)**: 정량 기준 부재 · 모호한 정도부사 · 주어·주체 불명확 · 조건 발생 시점 불명확
· 예외·경계 조건 누락 · 접속사 범위 모호 · 시간·일정 모호 · 기존 요구사항과 상충.
앞의 7개는 문장 치환 제안이 가능하고, 마지막 상충은 문장 수정으로 해결되지 않아 협의 대상으로만 표시한다.

**AI 판정 방식**: 규칙 기반 검출이 항상 먼저 실행되고, 그 위에 **사내 LLM API**
(GPT-OSS-120B · OpenAI 호환 `/v1/chat/completions`)를 한 번 더 호출해 보충한다.
폐쇄망이라 외부 AI API(Claude/GPT 등)는 쓸 수 없어 사내 LLM 하나만 쓴다. 사내 LLM이
응답하면 상세 화면에 `사내 LLM` 배지로, 응답하지 못하면(주소 미설정·연결 실패·타임아웃)
`AI 미응답` 배지로 표시되고 규칙 기반 결과만 남는다.

**사내 LLM 미응답 시**: 등록 자체는 막지 않는다. 규칙 기반 결과 그대로 저장되고
`AI 미응답`으로 표시되며, 나중에 "다시 분석"으로 재요청할 수 있다. 이는 **사내 LLM이
검토했지만 걸린 게 없는 경우와 구분해서** 표시한다 — 전자는 재분석이 필요하고 후자는
그대로 진행하면 되기 때문.

## 3. 기능 3 — 산출물 도출

범위: 확정 요구사항에서 개발 이슈와 산출물 4종을 **사내 고정 양식**으로 도출하고 추적한다.
화면·목업 상세는 [`screens/f3.html`](screens/f3.html) 참고.

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| FR-3-01 | 개발 이슈 도출 | 확정 요구사항 1건 → 개발 이슈 N개 자동 도출(이슈 분할 → 이슈별 본문 생성, 2단계 호출) | P0 |
| FR-3-02 | 4종 산출물 도출 | 이슈마다 SWVOC·기능 요구사항·비기능 요구사항·Detail Design 초안을 한 번에 생성 | P0 |
| FR-3-03 | 협업 완성 | AI 초안→사람 확정 / 사람 직접 초안→AI 완성. 항목마다 🤖 AI 도출 / 🖊 사람 작성 배지로 구분 | P0 |
| FR-3-04 | 산출물 편집·확정 | 편집·확정. 각 산출물 형식은 아래 사내 고정 양식을 그대로 따름 | P0 |
| FR-3-05 | 추적 링크 | 요구사항 ↔ 개발 이슈 ↔ 산출물을 ID로 연결, 변경 영향 조회 | P0 |

**개발 이슈 — 사내 고정 양식(3범주)**

| 범주 | 항목 | 설명 | 작성 주체 |
|---|---|---|---|
| 요구사항 접수 | 현상 기록 | 이 기능을 개발하게 된 배경 | 🖊 사람 — 현재 시스템 상태는 AI가 알 수 없음 |
| 요구사항 접수 | 개선 요청사항 | 고객사·내부에서 무엇을 원하는지 | 🤖 AI — 확정 본문·합의 기록에서 추출 |
| 요구사항 개발 | 변경 범위 | 어떤 모듈·DB가 바뀌는지, 영향 범위 | 🖊 사람 — 현재 코드 구조를 아는 담당자가 지정 |
| 요구사항 개발 | 제약 사항 | 성능·용량 등 지켜야 할 제약 | 🤖 AI |
| 변경점 설계 | 변경 전(As-Is) | 수정이면 이전 상태, 신규 개발이면 없음 | 🖊 사람 (신규 기능이면 AI가 "해당 없음"으로 채움) |
| 변경점 설계 | 변경 후(To-Be) | 개발 완료 후 예상 디자인·기능 | 🤖 AI |

날짜: **기한**(🖊 사람이 지정) · **생성일**(이슈 생성 시각, 시스템 자동) · **해결일**(확정 처리 시각, 시스템 자동).

**산출물 4종 — 사내 고정 양식**

| 산출물 | 구성 | 작성 주체 |
|---|---|---|
| SWVOC | 설명 → 1. 요청사항 → 2. 특이사항 | 🤖 AI (특이사항은 초안 — 다른 요구사항과의 관계 등 맥락 판단이 섞일 수 있어 사람 보완 권장) |
| 기능 요구사항 | 설명 → 1. 개요(역할·목적) → 2. 동작 정의(표) | 🤖 AI |
| 비기능 요구사항 | 기능 요구사항과 동일 구성 + **제약사항** 추가 | 🤖 AI |
| Detail Design | Class Diagram(영향 범위) · Sequence Diagram(변경 전/후, AS-IS·TO-BE) · 설명 | 🤖 AI — 다이어그램은 **Mermaid 문법(diagram-as-code)**으로 생성 후 화면에서 렌더링(AI가 이미지를 직접 그릴 수 없으므로) |

동작 정의 표 구조: **동작 유형(기본·예외) 2그룹 × 항목(선행조건·시나리오·후행조건) 3개 = 6행 고정**.
열은 `동작 유형 · 항목 · 내용` 3열 — 동작 유형 셀은 그룹당 rowspan 3으로 병합.

**AI 자동 추출 파이프라인** — 요구사항 1건에서 이슈·산출물까지 이어지는 3단계 LLM 호출.

1. **이슈 분할** — 확정 본문을 몇 개의 구현 단위(개발 이슈)로 나눌지를 판단(이슈 제목 N개 + 각 이슈가 커버하는 요구사항 부분). 한 번에 본문까지 시키면 이슈 경계가 흐릿해져서 분리한다.
2. **이슈 본문 생성**(이슈마다) — 위 3범주 양식을 JSON 하나로 채움.
3. **산출물 4종 생성**(이슈마다) — SWVOC·기능·비기능·Detail Design을 JSON 하나로 같이 생성.

**작성 주체 원칙**: 「확정 요구사항 + 정해진 양식」만으로 채울 수 있으면 **AI 도출**, 현재 코드·시스템 상태나 도메인 판단이 필요하면 **사람 작성**.
