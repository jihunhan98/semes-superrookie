# 요구사항 검출 개선과 제안 적용 UI 설계안

작성일: 2026-10-21  
대상: 요구사항 검출 → 수정 → 고객 합의 및 요구사항 확정  
작업 브랜치: `semes`  
상태: 설계 제안. 이 커밋은 Markdown 문서만 변경하며 기능·UI·DB·실행 빌드는 변경하지 않는다.

## 1. 바꾸려는 사용자 경험

현재 화면에서는 “2. 스텝 전환 조건 및 예외 처리”라는 제목의 “및”까지 범위가 모호하다고 검출한다. 제목에서 두 주제를 자연스럽게 나열한 표현이므로 이 사례는 검출하지 않아야 한다.

새 검토는 단어를 지적하는 대신, **서로 다른 구현 또는 시험 결과를 만들 수 있는 실제 문제**를 설명해야 한다. 사용자는 Beyond Compare처럼 좌우 본문을 비교하며 제안별로 적용하거나 원문을 유지하고, 오른쪽에서 최종 본문을 직접 수정한다.

목표는 다음과 같다.

- 제목·목차·자연스러운 나열에 대한 과잉 검출 줄이기.
- 문제가 된 문장, 서로 다른 해석, 구체적인 수정문을 함께 제공하기.
- 제안별 클릭으로 정확한 위치만 교체·추가하기.
- 근거가 없는 수치나 정책은 AI가 정하지 않고, 입력이 필요한 위치를 본문에서 표시하기.
- 확정될 본문은 내용 높이에 맞춰 펼쳐 보여주고 페이지 전체를 스크롤해 읽기.
- 기존 요구사항과의 비교 범위와 검토 성공·실패를 명확히 알리기.

## 2. 현재 코드를 확인한 결과

확인 기준은 `semes` 브랜치 커밋 `daedbfcc77b9858d271ac75c56c2f0e201138845`이다. 사용자의 로컬 실행본이 이 커밋과 같은지는 별도 확인하지 않았다.

| 확인 사항 | 현재 동작 | 영향 |
|---|---|---|
| “및” 검출 | `ai-model/rules.py`의 `PHRASE_RULES`에 단어 자체가 등록되어 있고, `detect()`가 본문 포함 여부로 검출 | 제목·목차·정상적인 나열도 검출 가능 |
| 규칙과 AI 결과 | `main.py:analyze()`에서 규칙 검출을 먼저 실행하고 LLM 결과를 합침 | LLM 프롬프트만 수정해도 규칙의 과잉 검출은 남음 |
| 기본 중요도 | `RequirementFinding`은 `severity=BLOCKING`, `resolutionState=OPEN`으로 생성 | 참고 의견도 확정을 막는 항목으로 저장될 수 있음 |
| 제안 내용 | 응답은 주로 `targetSpan/reason/suggestion`; 수정 위치와 교체문을 담은 구조화된 편집 목록 없음 | 설명을 읽고 사용자가 직접 수정해야 함 |
| 제안 숨기기 | `AiFindings.tsx`는 화면의 숨김 상태만 관리 | 숨겨도 서버의 미해결 상태는 바뀌지 않음 |
| 확정 본문 | 수정 화면이 `aiDraftContent`로 편집값을 초기화하고 재분석 후에도 이 값으로 교체 | 향후 수정 제안을 늘릴 때 사용자 편집을 덮어쓸 수 있음 |
| 본문 크기 | 고정된 textarea 기반, `.review-editor`는 최소 높이와 수동 크기 조절만 제공 | 긴 본문을 내부 스크롤로 확인해야 함 |
| AI 미응답 | 백엔드 `AiClient`는 빈 검출과 원문, `engine=unavailable`을 반환 | 검토 실패를 “문제 없음”으로 오해하지 않도록 구분 필요 |

### 2.1 이전에 등록한 요구사항도 검토하는가?

**현재 코드상 포함한다. 같은 프로젝트의 다른 요구사항 전체 본문을 전달한다.**

1. 최초 등록은 분석 작업을 큐에 넣고 `AiJobWorker.analyze()`에서 동일 프로젝트의 다른 요구사항을 조회한다.
2. 수정·재검토는 `RequirementService.diffAnalyze()` → `existingOf()`에서 동일 프로젝트의 다른 요구사항을 조회한다.
3. 두 경로 모두 자기 자신은 제외하고, 다른 요구사항의 `reqKey`와 `content`를 전달한다.
4. AI 서버는 이 목록을 규칙 검출에 넘기며, LLM 사용 시 `_all_requirements()`로 다른 요구사항 전문을 프롬프트에 붙인다.

조회 코드에는 확정 상태만 선택하는 필터가 없다. 따라서 “확정 요구사항만 비교한다”는 설명은 현재 구현과 다르다. 등록된 초안·보류 요구사항도 조회 결과에 포함될 수 있다. 별도 과거 버전 전체 이력이나 다른 프로젝트의 요구사항을 전달하는 구조도 아니다.

**전문을 전달한다는 사실과 충분히 검토했다는 사실은 다르다.**

- LLM이 비활성화되거나 실패하면 규칙 결과만 사용한다. 규칙의 기존 요구사항 비교는 제한된 우선순위 표현 등의 패턴 중심이므로 모든 의미적 모순을 찾는다고 볼 수 없다.
- LLM용 시스템 프롬프트는 모호성 유형 중심이고, 상충을 정식 응답 유형으로 명확하게 요구하지 않는다. 사용자 메시지에는 관련성·상충 판단 지시가 있지만 이 부분의 계약을 보강해야 한다.
- 수정 검토는 `_analysis_target()` / `_added_part()`에서 추가된 부분을 추출한다. 단순 접두 비교와 마침표 분리 방식이므로 제목 번호·소수·문맥·삭제에 따른 의미 변화를 정확하게 다루는 diff가 아니다. 추출 결과가 비면 전체 본문을 검토한다.
- 확인한 요청 생성 경로에는 다른 요구사항의 개수 제한이나 본문 잘라내기가 없다. 그러나 모델의 실제 컨텍스트 한도와 응답 품질, 실행 환경의 모델 설정까지 이 코드만으로 보장할 수는 없다.

## 3. 검출 기준: 단어보다 동작과 검증 결과

검출 카드는 최소한 다음 세 가지를 설명할 수 있어야 한다.

1. 어떤 원문 또는 기존 요구사항이 근거인가?
2. 어떤 구체적인 해석·조건·값이 달라지는가?
3. 그 차이 때문에 구현 또는 시험 결과가 어떻게 달라지는가?

“모호할 수 있음”, “예외 처리가 있으면 좋겠음”, “더 자세히 작성 필요”만으로는 검출 카드를 만들지 않는다. 필요한 정보가 다른 문단이나 참조된 요구사항에 이미 정의되어 있으면 그 근거를 먼저 확인한다.

### 3.1 검출하지 않을 사례

| 본문 예시 | 판단 | 이유 |
|---|---|---|
| “2. 스텝 전환 조건 및 예외 처리” | 검출하지 않음 | 제목의 주제 나열이며 실행 조건이 아님 |
| “로그 및 알람을 기록한다” | 접속사 이유로 검출하지 않음 | 두 대상이 명확함 |
| “A 및 B가 모두 충족되면 전환한다” | 검출하지 않음 | AND 조건 명시 |
| “A 또는 B 중 하나 이상이면 전환한다” | 검출하지 않음 | OR 조건 명시 |
| “통신 주기는 REQ-03에 따른다”, REQ-03에 주기 정의 존재 | 주기 누락으로 검출하지 않음 | 유효한 참조에서 기준 확인 가능 |
| 상단 용어 정의에서 가용 AMR을 정의하고 아래에서 재사용 | 재사용 구절 검출하지 않음 | 본문 문맥에 기준이 존재 |
| 오류 처리 정책이 별도 절에 명시됨 | 각 문장마다 예외 누락 검출하지 않음 | 공통 정책을 함께 읽어야 함 |
| 문체·맞춤법·긴 문장·중복 표현 | 기본 검출에서 제외 | 동작 차이가 없는 표현 개선은 본 검토 목적에서 제외 |

제목은 요구사항 단위를 구분하는 문맥으로 활용한다. 제목 형식이라도 “통신 주기 1초”처럼 실제 정책을 담고 있고 본문과 상충하면 그 **정책 차이**는 검토한다. 제목이라는 이유로 내용을 전부 무시하지 않는다.

### 3.2 검출할 사례와 제안 수준

| 유형 | 실제 검출 예시 | 필요한 설명과 제안 |
|---|---|---|
| 수치·단위 누락 | “응답이 없으면 재시도한다” + 응답 대기시간 기준 없음 | 어떤 시점부터 재시도하는지 시험할 수 없음을 설명. 대기시간·단위 입력 위치 제시 |
| 판단 기준 누락 | “가용 AMR을 선택한다” + 용어·참조에 가용 정의 없음 | 가용 판단에 필요한 상태·기준을 질문. IDLE·SOC 조건을 임의 확정하지 않음 |
| 실제 논리 모호성 | “A 또는 B 및 C이면 전환한다” | `(A OR B) AND C`와 `A OR (B AND C)`가 달라지는 사례 제시. 두 수정안을 선택지로 제공 |
| 경계값 상충 | 같은 매칭 대상·시점의 REQ-03은 SOC ≥50%, 현재는 SOC ≥30% | 양쪽 원문·비교 대상·단위와 30~50% 구간의 결과 차이 제시 |
| 조건 중첩 | 성공 처리와 실패 처리 조건이 같은 입력에서 동시에 성립 | 중첩되는 구체적 입력과 서로 다른 결과 제시. 우선순위 또는 조건 분리안 제공 |
| 주체 불명확 | 서버와 운영자 모두 등장한 뒤 “작업을 취소한다” | 어느 주체가 수행하느냐에 따른 자동/수동 처리 차이와 주체 선택안 제시 |
| 구현에 필요한 예외 누락 | 후보가 없으면 반환해야 하는 API인데 반환·대기 정책이 어디에도 없음 | 관련 흐름과 누락 근거를 설명. 대기/실패 중 선택하도록 제안 |
| 참조 오류 | 존재하지 않는 REQ-12를 기준으로 동작 | 참조 대상 부재 표시. ID 수정 또는 기준 직접 작성 제안 |
| 변경으로 생긴 불일치 | 제한값 변경 후 같은 문서의 예외 기준이 이전 값 유지 | 바뀐 절과 남은 절을 함께 보여주고 연결된 변경 제안 |

단순히 숫자가 다르다고 상충으로 판정하지 않는다. 같은 대상·속성·동작·적용 조건·시점인지 확인하고 단위와 부등호도 비교한다. “매칭 최소 SOC 30%”와 “충전 시작 SOC 50%”는 서로 다른 정책일 수 있다. 기본 정책과 명시적인 예외, 최신 합의에 의한 대체도 구분한다.

### 3.3 중요도와 확정 조건

| 분류 | 기준 | 확정 시 처리 제안 |
|---|---|---|
| 필수 확인 | 같은 조건에서 양립할 수 없는 동작·값이 구체적으로 확인됨 | 본문 수정 후 재검토, 또는 해당 항목에 고객 결정 근거 기록 |
| 확인 권장 | 동작 결정에 정보가 부족하지만 상충이 확정되지는 않음 | 미확인 상태를 알리되 원문 유지 가능 |
| 참고 | 동작에 영향을 주지 않는 표현 개선 | 기본 검출 목록에서 제외. 필요 시 별도 보기 |

모든 검출을 BLOCKING으로 생성하지 않는다. “필수 확인”은 모델의 확신 점수만으로 정하지 않고 양쪽 원문과 조건 일치 근거가 있어야 한다.

제안을 적용했다고 곧바로 “해결”로 간주하지 않는다. 현재 본문에 대해 재검토하고, 적용한 문장과 연결된 검출의 상태를 갱신한다. 원문 유지는 제안 거절 결정이며, 실제 모순을 해소했다는 뜻이 아니다.

미입력 표시가 본문에 남아 있으면 문장이 완성되지 않은 것이므로 확정을 막고 해당 위치로 이동시킨다. 검토가 실패했다면 완료·문제 없음으로 표시하지 않는다.

## 4. AI가 반환할 제안의 구체성

제안 한 건은 다음을 포함한다.

| 필드 | 의미 |
|---|---|
| 검출 ID·분석 ID·기준 본문 해시 | 어떤 분석과 본문에 대한 제안인지 식별 |
| 유형·중요도 | 모순, 조건 모호성, 참조 오류 등과 처리 수준 |
| 문제 위치 | 절·문장 ID, 문장 내 시작/끝, 원문 구절, 앞뒤 문맥 |
| 원문 근거 | 현재 문장과 관련 기존 요구사항 ID·본문·상태·버전 |
| 문제 설명 | 서로 다른 해석과 구체적인 결과 차이 |
| 제안문 | 본문에 들어갈 완성된 문장 또는 명시적인 입력 템플릿 |
| 변경 연산 | REPLACE / INSERT_BEFORE / INSERT_AFTER / DELETE |
| 변경 전 구절 | 실제 교체할 정확한 원문. 전체 본문이 아님 |
| 변경 후 구절 | 설명이 아닌 삽입 가능한 본문 |
| 확인할 값 | 미확정 값·선택지·단위·질문·입력 위치 |
| 제안 근거 | 원문 유지·표현 정리·어느 요구사항의 어떤 근거 사용 여부 |
| 연관·충돌 제안 | 함께 적용할 제안, 같은 위치에 적용할 수 없는 대안 |

### 4.1 그대로 적용 가능한 제안

원문: “A 또는 B 및 C이면 다음 스텝으로 전환한다.”

- 문제: `(A OR B) AND C`와 `A OR (B AND C)` 중 어느 조건인지 다르다.
- 차이 예시: A=true, B=false, C=false이면 첫 해석은 전환하지 않고 두 번째 해석은 전환한다.
- 제안 A: “A 또는 B 중 하나 이상이 충족되고, C도 충족되면 다음 스텝으로 전환한다.”
- 제안 B: “A가 충족되거나, B와 C가 모두 충족되면 다음 스텝으로 전환한다.”
- UI: 각 제안의 미리보기를 제공하고 하나를 선택해 적용한다. AI가 둘 중 하나를 기본 정책으로 확정하지 않는다.

### 4.2 값 확인이 필요한 제안

원문: “응답이 없으면 재시도한다.”

제안문:

> 요청 전송 후 ⟦응답 대기시간: 입력 필요, 단위 ms⟧ 이내에 응답이 없으면, ⟦재시도 간격: 입력 필요, 단위 ms⟧마다 최대 ⟦재시도 횟수: 입력 필요⟧회 재시도한다. 이후 처리는 ⟦실패 처리 정책: 입력 필요⟧에 따른다.

- 버튼은 “템플릿 적용”으로 표시한다. 완성된 확정문처럼 보이지 않게 한다.
- 정책에 따라 이 항목들이 필요한 이유를 개별 설명한다. 기존 공통 정책이 있으면 그 정책을 참조하고 중복 입력을 요구하지 않는다.
- 오른쪽에 적용된 문장의 바뀐 부분은 파란 강조, 미입력 값은 주황 밑줄과 “입력 필요” 배지로 표시한다.
- 미입력 값은 클릭해서 입력하거나 원문 유지로 되돌릴 수 있다.
- 강조만 지워서 완료 처리하지 않는다. 값이 채워졌거나 문장 편집으로 해당 질문이 해소됐는지 확인한다.
- AI가 1초·3회 같은 임의 값을 넣지 않는다. 예시 값은 도움말로만 구분한다.

### 4.3 기존 요구사항과 값이 다를 때

기존 REQ-03: “작업 매칭 시 SOC 50% 이상인 AMR만 후보에 포함한다.”  
현재 REQ-11: “작업 매칭 시 SOC 30% 이상인 AMR을 후보에 포함한다.”

보여줄 내용:

- 비교 속성: 작업 매칭 후보의 최소 SOC.
- 적용 조건: 같은 프로젝트, 같은 작업 매칭 정책이라는 근거.
- 결과 차이: SOC 40% AMR은 REQ-03에서는 제외, REQ-11에서는 포함.
- 선택 1: 현재 문장을 REQ-03의 50% 기준에 맞추는 제안을 적용.
- 선택 2: 30%가 새 고객 합의라면 현재 본문 유지, 대체할 기존 요구사항과 고객 결정 근거 기록.
- 선택 3: 서로 다른 적용 조건이면 조건 구분 문장을 작성.

다른 요구사항의 본문을 이 화면에서 자동 수정하지 않는다. 다른 문서 변경이 필요하면 ID와 필요한 변경을 보여주고 그 요구사항의 별도 수정·합의 과정으로 연결한다. 기존 문서가 바뀌기 전까지 문서 간 불일치를 해결됐다고 표시하지 않는다.

## 5. 좌우 비교 UI

### 5.1 기본 구성

| 영역 | 표시와 동작 |
|---|---|
| 상단 | 요구사항 ID, 기준 버전, 검토 상태, 비교한 요구사항 수, 이전/다음 제안 |
| 왼쪽 약 48% | 이번 검토의 기준 본문. 읽기 전용, 삭제·교체될 부분 강조 |
| 가운데 약 4% | 제안별 “→ 적용”, “원문 유지”, 적용 후 “되돌리기”. 툴팁과 접근 가능한 이름 제공 |
| 오른쪽 약 48% | 확정될 본문. 직접 편집 가능, 적용된 수정·미입력 값 강조 |
| 선택한 제안의 상세 | 해당 문장 아래 펼쳐서 이유·변경 전후·관련 요구사항·선택지 표시 |
| 하단 | 적용·원문 유지·미입력·재검토 필요 수, 다시 검토, 합의 및 확정 |

왼쪽은 분석 당시 본문으로 고정한다. 기존 저장 본문과 분석 당시 편집 본문이 다르면 상단에 기준을 명시한다. 다른 요구사항과 충돌한 항목은 원문 비교를 별도 확장해 보여주고 기존 문서 ID·버전을 표시한다.

좌우 문단은 절/문장 단위로 대응시킨다. 한쪽 문장이 길어졌다면 대응 구간의 여백으로 위치를 맞추며, 본문에 줄바꿈을 추가해 정렬하지 않는다. 최종 저장본에는 정렬용 여백·하이라이트·배지가 들어가지 않는다.

### 5.2 본문을 한 번에 펼쳐 보기

- 두 본문은 자동 높이로 펼친다. 고정 높이 textarea의 내부 세로 스크롤과 max-height 제한을 없앤다.
- 페이지 전체 세로 스크롤 하나로 긴 문서를 읽는다. 긴 문서를 화면 한 장에 축소한다는 의미는 아니다.
- 줄바꿈·문단 번호·목록 구조를 보존하고 가로로 긴 문장은 화면 너비에 맞춰 줄바꿈한다.
- 상단 제안 이동과 현재 절 표시를 고정해 긴 문서에서 위치를 찾게 한다.
- “본문 넓게 보기”로 사이드바를 접고 두 본문에 화면 폭을 배정한다.
- 좁은 화면에서는 원문/확정 본문 전환 또는 위아래 비교를 제공하되, 같은 제안 위치를 유지한다.

### 5.3 색상과 위치 찾기

| 표시 | 의미 |
|---|---|
| 왼쪽 붉은 취소선 + “교체 전” | 교체·삭제 대상 |
| 오른쪽 파란 배경 + “적용됨” | 제안 또는 사용자 편집으로 바뀐 부분 |
| 주황 밑줄 + “입력 필요” | 사용자가 결정해야 하는 값·정책 |
| 보라 테두리 + “기존 요구사항 확인” | 다른 요구사항과 비교가 필요한 부분 |

색만으로 구분하지 않는다. 배지·아이콘·설명과 이전/다음 이동을 함께 제공한다. 적용 직후 해당 구간을 잠깐 강조하고 화면 안으로 이동시키되 키보드 입력 중인 다른 위치를 강제로 이동하지 않는다.

## 6. 적용 버튼이 실제로 바꾸는 것

### 6.1 교체·추가·삭제

| 연산 | 클릭 시 동작 | 원문 처리 |
|---|---|---|
| REPLACE | 선택 문장 또는 구절을 제안문으로 교체 | 기존 해당 구절 제거 후 같은 위치에 삽입. 다른 문장 보존 |
| INSERT_BEFORE / AFTER | 지정 문장 앞/뒤에 필요한 문장을 추가 | 기준 문장은 유지 |
| DELETE | 삭제 미리보기 후 선택한 구절만 제거 | “삭제 적용”임을 명시. 일반 적용과 구별 |
| 대안 선택 | 여러 정책 제안 중 하나를 선택해 위 연산 수행 | 같은 문제의 다른 대안은 동시에 적용하지 않음 |

설명문인 suggestion 전체를 붙여넣지 않는다. 변경 후 본문 필드만 사용한다. 단어 전체 replace로 같은 표현을 문서 전체에서 바꾸지 않는다.

### 6.2 잘못된 위치에 반영하지 않기

- 분석 스냅샷의 본문 해시와 제안의 대상 위치를 검증한다.
- 서버는 AI가 반환한 문장 ID·구절·문맥이 실제 스냅샷에 있는지 확인하고 편집 범위를 검증한다.
- 프론트는 검증된 문장 단위 위치를 편집기 변경 이력에 따라 이동시킨다. JavaScript/Python의 문자 인덱스 차이를 피하도록 화면에서는 UTF-16 인덱스로 통일한다.
- “및”처럼 반복되는 짧은 구절 하나로 위치를 식별하지 않는다. 문장 ID·문맥·변경 전 구절을 함께 사용한다.
- 사용자가 대상 구간을 이미 수정했다면 “본문이 바뀌어 다시 확인이 필요합니다”로 전환한다. 유사 문자열을 찾아 임의로 덮어쓰지 않는다.
- 앞 제안을 적용해 뒤쪽 위치가 이동한 경우 편집기 위치 매핑으로 갱신한다. 매핑이 확실하지 않은 제안은 적용을 잠그고 재검토한다.
- 겹치는 두 제안은 충돌 관계로 묶고, 한쪽 적용 시 다른 제안은 다시 확인하게 한다.
- 여러 위치를 함께 바꿔야 의미가 맞는 제안은 하나의 변경 묶음으로 미리보기하고 전부 적용하거나 전부 취소한다.
- 같은 버튼을 반복 클릭해 중복 삽입하지 않는다. 적용 상태를 저장하고 버튼을 “되돌리기”로 바꾼다.

되돌리기는 해당 적용 이후의 사용자 편집을 보존해야 한다. 같은 구간을 사용자가 다시 수정했다면 예전 문장을 바로 덮지 않고 되돌릴 변경을 비교해서 선택하게 한다. 일반 편집기 실행 취소도 지원한다.

## 7. 검토·편집·확정 흐름

1. 현재 편집 본문과 같은 프로젝트의 다른 요구사항 전체를 스냅샷으로 확보한다.
2. 제목·용어 정의·공통 정책·참조를 읽은 뒤 문맥에 근거한 후보만 만든다.
3. 양쪽 근거와 제안의 편집 위치·내용을 검증해 제안 목록을 제공한다.
4. 오른쪽 초기값은 사용자가 작성한 현재 본문으로 둔다. 제안을 자동 일괄 반영하지 않는다.
5. 사용자는 개별 제안 적용, 대안 선택, 템플릿 적용, 원문 유지 또는 직접 수정을 한다.
6. 바뀐 구간과 미입력 위치를 강조하고 개별 변경 이력을 보존한다.
7. “다시 검토”는 현재 오른쪽 본문으로 새 분석을 수행한다. 편집 본문을 AI 초안으로 덮어쓰지 않는다.
8. 새 결과는 이전 결과를 대체하되 사용자 결정 이력은 남긴다. 같은 근거·같은 문장에 대한 원문 유지 결정은 유지할 수 있고, 문맥·관련 요구사항이 바뀌면 다시 확인한다.
9. 현재 본문 해시와 비교 요구사항 버전이 검토 시점과 같은지 확인한다. 바뀌었다면 재검토 대상으로 표시한다.
10. 미입력 값과 남은 필수 확인 항목의 위치·이유를 보여준다. 필수 확인 항목을 수용할 때는 해당 항목별 고객 결정 근거를 기록한다.
11. 고객 합의 스냅샷과 실제 확정할 본문을 일치시켜 확정한다. 합의 후 본문을 바꾸면 다시 합의해야 한다.

“숨기기”와 “원문 유지”는 구분한다. 숨기기는 화면 표시 설정이며 검토 결정이 아니다. 원문 유지 결정은 서버에 저장하고 “문제 아님 / 적용 대상 아님 / 고객 결정으로 유지” 등을 구분한다.

## 8. AI 요청과 검증 설계

### 8.1 전달할 데이터

| 데이터 | 전달 이유 |
|---|---|
| 현재 요구사항 ID·현재 편집 본문 전체 | 제목·정의·앞뒤 문맥을 읽기 |
| 저장 기준 본문·버전, 실제 변경 구간·수정 사유 | 바뀐 의도와 삭제 영향 판단 |
| 동일 프로젝트의 다른 요구사항 전체 본문·ID·상태·버전 | 상충과 참조 확인, 초안과 확정 근거 구별 |
| 문장 ID와 절 구조 | 편집 위치를 안정적으로 식별 |
| 이전 검토 결정과 근거 | 같은 문맥에서 거절한 제안을 반복하지 않기 |

확정 요구사항은 공식 비교 기준, 초안·보류 요구사항은 “확정 전 문서와 차이”로 구분한다. 초안과 다르다는 이유만으로 필수 상충으로 확정하지 않는다.

현재 본문 전체와 변경 전후를 함께 전달하고 변경 구간을 우선 검토한다. 삭제 때문에 사라진 정책과, 변경되지 않았지만 영향을 받는 같은 본문의 문장도 검토한다. 등록해 둔 요구사항을 일부만 고른 뒤 전체 검토했다고 표시하지 않는다.

모델 한도를 넘으면 동일 프로젝트 요구사항을 빠짐없이 나누어 현재 본문 전체와 함께 비교하고 결과를 합친다. 각 배치의 대상 ID·본문 해시·성공 여부를 기록하며 일부 실패는 “부분 검토”로 표시한다. 사용자에게 “프로젝트 기존 요구사항 24/24건 검토 완료”처럼 처리 범위를 보여준다.

### 8.2 프롬프트에 명시할 핵심 지시안

> 제목·목차·단순 나열의 “및”, “등” 자체를 문제로 검출하지 마세요.  
> 현재 본문 전체와 용어 정의·참조 요구사항을 먼저 읽으세요.  
> 실제로 다른 구현·시험 결과를 만드는 해석 차이 또는 누락만 제시하세요.  
> 문장에 없는 예외·수치·업무 정책을 임의로 확정하지 마세요.  
> 기존 문서와 상충을 주장하면 양쪽 원문, 같은 적용 조건, 결과 차이를 제시하세요.  
> 수정 제안은 바로 들어갈 본문과 편집 연산으로 제공하세요. 설명과 교체문을 분리하세요.  
> 근거가 없는 결정은 입력 필요 항목 또는 복수 대안으로 제시하세요.  
> 같은 원인의 검출을 반복하지 마세요. 문제가 없으면 빈 목록을 반환하세요.

이 지시만으로 완료하지 않는다. 규칙의 단어 단독 검출을 제거하고, 규칙 후보에도 문맥 확인 기준을 적용해야 한다. 규칙 기반 동작만 가능한 경우에도 같은 과잉 검출 기준을 따른다.

### 8.3 결과 검증

- 원문 인용·관련 ID·상태·버전이 실제 입력과 일치하는지 검사한다.
- 수정 위치가 유효하고 변경 전 구절이 정확하게 일치하는지 검사한다.
- 범위를 벗어난 교체, 의미와 무관한 대량 삭제, 겹치는 대안의 동시 적용을 방지한다.
- 원문에 근거가 없는 숫자·정책은 근거 출처를 요구하고, 확인할 수 없으면 사용자 입력으로 전환한다.
- 문제가 없다는 설명과 수정 연산이 함께 오는 등 모순된 응답은 제안에서 제외하고 결과 불완전을 표시한다.
- AI 오류·응답 누락·일부 배치 실패를 “검출 0건” 성공으로 표시하지 않는다.

## 9. 개발 시 변경할 위치 제안

아래는 변경 예정 지점이며 이번 문서 커밋에서 구현하지 않는다.

| 파일/영역 | 변경 방향 |
|---|---|
| `ai-model/rules.py` | “및” 등 단어 단독 검출 제거, 문맥에 근거한 후보 생성, 반복 검출 정리 |
| `ai-model/main.py` | 전체 문맥+변경 전후 입력, 구조화된 제안 응답, 기존 요구사항 상충 근거 계약 |
| `RequirementService` / `AiJobWorker` | 동일한 입력 스냅샷 계약, 기존 요구사항 상태·버전 전달, 오래된 결과 구분 |
| AI DTO·검출 저장 모델 | 중요도·편집 연산·위치·미입력 값·결정 이력 저장 |
| `AiFindings.tsx` | 설명 카드 중심에서 원문·제안·적용 상태 연결로 확장 |
| 요구사항 수정 `edit/page.tsx` | 좌우 비교, 직접 수정, 제안별 적용·되돌리기, 사용자 본문 유지 |
| `frontend/app/globals.css` 및 편집기 | 자동 높이, 페이지 단일 스크롤, 넓게 보기와 변경 강조 |
| 확정 처리 | 최신 본문과 검토·합의 일치 확인, 미입력 및 항목별 필수 확인 근거 안내 |

기존 알림 설계 `docs/requirement-conflict-notifications.md`는 저장 후 다른 요구사항 간 차이를 알려주는 기능이다. 이 문서는 **확정 전 본문 검토와 사용자가 선택하는 수정 제안**의 추가 설계이며, 알림 읽음 처리만으로 본문을 수정하거나 충돌을 해결하지 않는다.

## 10. 구현 후 확인할 시나리오

| 시나리오 | 기대 결과 |
|---|---|
| 제목 “2. 스텝 전환 조건 및 예외 처리” | 검출 없음 |
| 자연스러운 나열에 “및” 여러 번 등장 | 단어 단위 검출 없음 |
| A 또는 B 및 C 조건 | 실제 해석 차이와 두 수정안 표시 |
| 같은 본문 앞에서 용어·주기 정의 | 정의된 항목을 누락으로 다시 검출하지 않음 |
| 다른 요구사항에 기준 존재 | ID·원문을 근거로 활용 |
| 동일 대상 SOC 50% vs 30% | 양쪽 원문과 40% 입력에서의 결과 차이 표시 |
| 매칭 기준 30%와 충전 시작 기준 50% | 숫자 차이만으로 상충 검출하지 않음 |
| 기본값과 명시적 예외 | 예외 관계가 일관되면 상충 없음 |
| 한 문장 제안 적용 | 대상 문장만 교체, 원문 중복·전체 덮어쓰기 없음 |
| 삽입·삭제 제안 적용 | 연산대로 지정 위치만 변경 |
| 같은 표현이 여러 곳에 등장 | 선택 위치만 변경 |
| 한 제안 적용 후 다른 위치 적용 | 위치 이동 반영, 잘못된 곳 교체 없음 |
| 같은 구간에 대안 두 개 | 하나만 적용 가능 |
| 사용자 직접 수정 후 오래된 제안 적용 | 재확인 안내, 사용자 편집 보존 |
| 적용 뒤 직접 수정한 곳 되돌리기 | 수정 충돌 표시, 무조건 덮어쓰지 않음 |
| 재시도 정책 근거 없음 | 임의 수치 없이 입력 템플릿 제공 |
| 미입력 템플릿 적용 후 확정 | 남은 위치로 안내, 완성 전 확정 차단 |
| 긴 요구사항 | 본문 내부 세로 스크롤 없이 전체 펼침, 페이지로 탐색 |
| 재분석 | 오른쪽 사용자 본문 보존, 분석 결과만 갱신 |
| 제안 숨기기 / 원문 유지 | 표시 설정과 서버 결정 이력을 구분 |
| 프로젝트 다른 요구사항 추가 | 비교 목록에 포함, 검토 대상 수 갱신 |
| LLM 실패·일부 비교 실패 | 규칙 검토/부분 검토/실패 상태를 구분 |
| 합의 후 본문 변경 | 합의 스냅샷 불일치를 명시하고 재합의 요구 |

이번 단계의 완료 기준은 이 설계를 Git에서 검토할 수 있는 상태로 제공하는 것이다. 기능 개발은 별도 요청 후 진행한다.
