왜 한 번의 호출로 안 끝나는가

"요구사항 하나 → 이슈 N개 → 이슈마다 산출물 4종"은 2단계 호출로 나눈다. 이슈를 몇 개로 쪼갤지부터 정해야 그 다음에 이슈별 본문·산출물을 채울 수 있기 때문 — 한 번에 다 시키면 이슈 경계가 흐릿해진다(스토리 하나에 서로 다른 기능이 섞여 버림).

1

입력 수집

확정된 요구사항 본문(v1.0.0 이상)과 프로젝트 내 관련 모듈·기존 이슈 목록을 컨텍스트로 모은다.

→
2

이슈 분할 (1차 호출)

"구현 단위로 몇 개의 개발 이슈로 나눌지"만 판단 — 이슈 제목 N개 + 각 이슈가 커버하는 요구사항 부분(인용).

→
3

이슈 본문 생성 (2차 호출·이슈마다)

<요구사항 접수>·<개발>·<변경점 설계> 3범주를 사내 고정 양식 JSON으로 채운다.

→
4

산출물 4종 생성 (3차 호출·이슈마다)

SWVOC·기능·비기능·Detail Design을 한 이슈당 JSON 하나로 같이 생성한다.

→
5

사람 검토

🖊 배지 붙은 항목만 사람이 채우고, 🤖 항목은 확인 후 확정만 하면 된다.

응답 스키마 — 이슈 본문 / 산출물 4종
// 2차 호출 — 개발 이슈 본문
{

    "phenomenon": string,      // 🖊 사람
    "improvementRequest": string // 🤖 AI
  },
  "development": {               // 요구사항 개발
    "changeScope": string,     // 🖊 사람
    "constraints": string     // 🤖 AI
  },
  "changeDesign": {              // 변경점 설계
    "before": string | null, // 🖊 사람(신규 기능이면 AI가 null)
    "after": string          // 🤖 AI
  },
  "dueDate": null,             // 🖊 사람이 나중에 지정
  "createdAt": "auto",        // 시스템 자동(이슈 생성 시각)
  "resolvedAt": null          // 시스템 자동(확정 처리 시각)
}

  },
  "functional": {                // 기능 요구사항
    "description": string, "role": string, "purpose": string,
    "behaviors": [               // 기본 3행 + 예외 3행 고정
      {

        "item": "선행조건"|"시나리오"|"후행조건",
        "content": string

    ]
  },

    "description": string
  }
}

가용 AMR 매칭

설명 🤖 AI 도출
req-ta-01의 "가용 AMR 매칭" 부분을 개발 관점으로 옮긴 기능. Host의 할당 요청을 받아 조건에 맞는 AMR을 골라 매칭하는 흐름을 정의한다.
1. 개요 🤖 AI 도출
역할Host의 태스크 할당 요청에 대해 조건을 만족하는 가용 AMR을 선별·매칭한다.
목적할당 지연·오배정을 방지하고 우선순위에 따라 최적의 AMR을 배정한다.
2. 동작 정의 🤖 AI 도출 · 동작 유형 2그룹(기본·예외) × 항목(선행조건·시나리오·후행조건)
동작 유형항목내용
기본정상 흐름 선행조건가용 AMR ≥ 1대, 요청이 스키마에 맞게 유효함
시나리오요청 수신 → 가용 필터(IDLE·SoC 충분·에러 없음) → 우선순위(SoC 높은 순) 정렬 → 최상위 매칭 → 결과 회신
후행조건매칭된 AMR 1대의 상태가 BUSY로 전환되고, 요청자에게 매칭 결과가 회신됨
예외오류·실패 선행조건가용 필터를 통과한 AMR이 0대이거나, 요청 필수 필드가 누락됨
시나리오가용 0대 → 대기(PENDING) 등록 후 가용 변화 이벤트 구독 / 필드 누락 → 스키마 검증 단계에서 즉시 거절
후행조건가용 0대 시 PENDING 상태로 대기 등록됨 · 필드 누락 시 400 오류 코드로 회신되고 매칭은 수행되지 않음
🤖 AI 도출 — 전 항목 자동 작성. 기능 요구사항은 「확정된 요구사항 + 이 개발 이슈의 제약사항」만으로 채울 수 있어, 사람은 검토 후 확정만 하면 됩니다.

매칭 성능·가용성

설명 🤖 AI 도출
가용 AMR 매칭 기능이 지켜야 할 성능·가용성 품질 속성. req-ta-01의 응답 기준과 이 개발 이슈의 제약사항을 정량 지표로 재정리한다.
1. 개요 🤖 AI 도출
역할매칭 응답 속도와 동시 요청 처리 순서를 보장해 서비스 품질을 유지한다.
목적Host 다건 요청이 몰려도 지연·역전 없이 안정적으로 매칭 결과를 회신한다.
2. 동작 정의 🤖 AI 도출 · 기능 요구사항과 같은 표 구조
동작 유형항목내용
기본정상 흐름 선행조건초당 요청 수가 설계 한도(TPS) 이내
시나리오요청 도착 순서대로 큐잉 → 매칭 로직 처리 → 200ms 이내 회신
후행조건모든 응답이 200ms 이내로 회신되고, 처리 순서가 도착 순서와 일치함
예외오류·실패 선행조건순간 요청량이 설계 한도(TPS)를 초과함
시나리오초과분은 큐에 대기 → 우선순위 규칙에 따라 순차 처리, 임계 초과 시 초과 요청 거절
후행조건큐 대기 시간이 SLA(1초)를 넘기지 않고, 초과 거절분은 오류로 명확히 회신됨
제약사항 🤖 AI 도출
매칭 응답 200ms 이내(P99) · 동시 요청 시 우선순위 큐 순서 보장 · 상태 전환은 원자적(atomic) 처리로 이중 배정 방지 · 큐 대기 SLA 1초 초과 시 오류 회신.
🤖 AI 도출 — 전 항목 자동 작성. 기능 요구사항과 같은 근거(확정 요구사항 + 제약사항)로 채워지고, 구조도 동일하다 — 마지막에 제약사항 항목만 더 있다.

Sequence Diagram — 변경 전/후 🤖 AI 도출
AS-IS
1Host → JobAssignService: 할당 요청
2JobAssignService → AmrAvailabilityFilter: 가용 목록 조회
3JobAssignService: 거리순 정렬
4JobAssignService → Host: 매칭 결과 회신
TO-BE
1Host → JobAssignService: 할당 요청
2JobAssignService → AmrAvailabilityFilter: 가용 목록 조회
3JobAssignService → PriorityQueue: SoC 우선순위로 정렬 요청
4PriorityQueue: 동점 시 대기시간 최장 우선
5JobAssignService → Host: 매칭 결과 회신
설명 🤖 AI 도출
기존에는 "거리순"으로 정렬했지만, req-ta-01 확정에 따라 PriorityQueue를 거쳐 SoC(배터리 잔량) 높은 순으로 정렬하도록 변경한다. 동점 시 대기시간이 가장 긴 AMR을 우선한다.
🎨 이미지가 아니라 코드. AI는 위 다이어그램을 Mermaid 문법 텍스트로 생성한다 — 화면은 그 텍스트를 그대로 렌더링한 결과다. "Mermaid 코드 보기" 버튼으로 원본 텍스트를 확인·수정할 수 있다.
