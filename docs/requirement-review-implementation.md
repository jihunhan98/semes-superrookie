# 요구사항 검토·제안 적용 사용 안내

2026-10-21 · 작업 브랜치 `semes`

## 적용 순서

1. `semes`의 최신 소스와 `frontend/dist/standalone`을 받는다.
2. 기존 DB에서는 `db/init.sql`을 DBeaver의 SQL 스크립트 실행으로 **한 번만** 실행한다. V007과 동일하므로 두 파일을 모두 실행하지 않는다.
3. 백엔드와 AI 서버를 새 소스로 다시 시작하고 프론트도 다시 시작한다. AI 서버 주소·로컬 설정·설치 라이브러리는 변경하지 않았다. 새 Python 의존성은 없다.
4. 기존에 등록한 요구사항은 수정 화면에서 **AI 재검토**를 한 번 실행한다. 이전의 단어 기반 검출 결과를 새 문맥 검토 결과로 갱신한다.

이번 SQL은 기존 테이블에 CLOB 컬럼 2개를 추가하고 기존 한국어 문자열 컬럼 3개의 길이를 CHAR 기준으로 맞춘다. 테이블 재생성·초기 데이터 삽입은 없다. 아직 Jira 테이블 자체가 없는 환경은 V006을 별도로 적용해야 한다.

## 검출이 달라진 점

- “2. 스텝 전환 조건 및 예외 처리”, “로그 및 알람을 기록한다” 같은 제목·나열은 접속사만으로 지적하지 않는다.
- “A 또는 B 및 C이면 전환한다”는 실제 논리 차이와 두 대안을 제시한다.
- 정의·참조에서 확인할 수 있는 기준을 누락으로 반복 지적하지 않는다.
- 응답 대기시간 등 근거가 없는 값은 임의 수치로 채우지 않고 입력 템플릿을 제안한다.
- 같은 프로젝트의 기존 요구사항 전체를 상태·버전과 함께 전달한다. 수정 중인 본문도 일부 추출하지 않고 전체 문맥과 변경 전 본문을 보낸다.
- 숫자만 다르다고 무조건 필수 확인으로 저장하지 않는다. 확정 문서의 양쪽 근거가 있는 상충만 필수 확인 후보가 된다. 규칙만으로 동일 조건을 증명하기 어려우면 확인 권장으로 남긴다.

## 화면 사용 방법

1. 왼쪽은 이번 검토의 기준 본문, 오른쪽은 확정될 본문이다. 본문은 내용 높이로 펼쳐지고 페이지 전체를 스크롤한다. “본문 넓게 보기”로 메뉴를 접을 수 있다.
2. 아래 목록에서 제안을 선택하면 문제 문장·근거·해석 차이·구체적인 수정안이 나온다. “원문 위치 보기”와 “수정 위치 보기”로 해당 구간을 찾는다.
3. “이 제안 적용”은 선택 문장만 교체한다. 삽입은 원문을 유지하고 앞/뒤에 추가하며 삭제는 별도 “삭제 적용”으로 표시한다. 여러 대안은 하나를 선택한다.
4. 적용된 구간은 파랑, 미입력 값은 주황으로 표시한다. 주황색 위치 버튼을 누르면 본문에서 값을 선택해 바로 입력할 수 있다.
5. 적용·되돌리기·원문 유지 결정은 서버에 이력을 남긴다. 제안을 적용했다고 검출이 해결된 것으로 처리하지 않는다.
6. 다른 제안이나 직접 편집과 겹친 수정안은 재검토 전 적용할 수 없다. 적용한 구간을 다시 편집한 경우 되돌리기가 그 편집을 덮어쓰지 않는다.
7. 현재 본문으로 “AI 재검토”를 실행한다. 직접 편집한 오른쪽 본문은 덮어쓰지 않는다. 새 분석에서는 이전 제안의 위치·적용 기록을 새로 시작하며 과거 결정은 서버 이력에 보존한다.
8. 입력 표시가 모두 사라지고 현재 본문에 대한 검토가 준비되면 고객 합의 후 확정한다. 남아 있는 필수 확인 항목마다 고객 결정 근거를 입력한다.

적용 위치·실행 취소를 위한 편집 상태와 작성 중 본문은 현재 브라우저의 세션 저장소에도 보존한다. 같은 탭을 새로고침했을 때 복원되며, 다른 기기까지 작성 중 본문을 동기화하는 기능은 아니다. 원문 유지 결정은 동일 본문·동일 기존 요구사항 스냅샷일 때 재검토에서도 유지하며, 근거가 바뀌면 다시 검토한다.

## 검토·확정 상태

- 전체 배치가 성공하면 검토한 기존 요구사항 수를 표시한다.
- 규칙만 실행했다면 “규칙 검토 완료 / AI 문맥 검토 미완료”로 표시한다. 이 상태에서도 사용자가 읽고 합의해 확정할 수 있다.
- AI 호출 실패·부분 실패는 성공 0건으로 보이지 않는다. 재검토해야 한다.
- 본문을 고쳤거나 다른 요구사항의 본문·상태·버전이 바뀌었다면 서버에서도 재검토를 요구한다.
- `⟦…⟧` 입력 표시가 남아 있으면 화면과 API 양쪽에서 확정을 막는다.
- 원문 유지는 제안을 사용하지 않겠다는 기록이다. 필수 상충의 고객 결정 근거까지 자동으로 대체하지 않는다.

## 검증 범위

Python의 문맥 검출·대안·수치 상충·참조·전체 본문 전달·배치·실패 상태, 편집 위치 이동·반복 문구·삽입·삭제·사용자 편집 보호, 백엔드 저장·확정 조건을 자동 검사한다. 프론트는 타입 검사와 프로덕션 standalone 빌드를 수행한다.

브라우저에서는 API 응답을 테스트 데이터로 연결해 긴 본문 전체 펼침, 템플릿 적용, 새로고침 복원, 되돌리기, 직접 수정 보호, 재검토 본문 보존과 좁은 화면을 확인한다. 실제 Oracle DB 마이그레이션과 사내 LLM 응답 품질은 이 실행 환경에서 직접 확인하지 못한다. 백엔드 자동 테스트는 이 환경의 JDK 17에서 `-Djava.version=17`로 실행하며, 프로젝트의 Java 21 설정은 그대로 유지한다.

자동 검사 결과: Python 37건, 프론트 단위 검사 13건과 경로 검사 1건을 통과했다. 백엔드 검사는 로컬 FastAPI를 실행한 HTTP 계약 검사까지 포함한다.

실행용 패키지에는 Next.js 미리보기 ID·서명 키·암호화 키를 포함하지 않는다. 시작할 때 생성하며 패키징 단계에서도 빈 값인지 검사한다. 실행 검증 후에는 배포 파일을 다시 정리해 생성된 키가 커밋되지 않게 한다.

## 검출 유형 통합

현재 유형은 수치·판단 기준 불명확 / 수행 주체 불명확 / 동작 조건 불명확 / 예외 처리 누락 / 기존 요구사항과 상충의 5개다. 시간·주기·대기시간·횟수 누락과 모호한 정도 표현은 첫 번째 유형으로, 발생 조건과 접속사 논리는 세 번째 유형으로 묶는다. 참조 요구사항 확인 필요는 제외한다.

이 유형 정리 변경 자체는 SQL 실행과 프론트 재빌드가 필요 없다. 기존 단계의 DB 변경을 이미 적용한 환경에서는 백엔드·AI 서버만 다시 시작하면 된다. 이전 결과도 새 유형으로 표시하고 참조 항목은 확정을 막지 않는다. 기존 요구사항 본문을 포함한 상충 검토는 유지한다.
