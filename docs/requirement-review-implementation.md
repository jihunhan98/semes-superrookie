# 요구사항 검토·제안 반영 사용 안내

2026-10-30 · 작업 브랜치 `semes`

## 실행

최신 소스와 `frontend/dist/standalone`을 받은 뒤 AI 서버와 프론트를 다시 시작한다. `run-all.bat`으로 실행하는 환경에서도 새 standalone 파일이 사용된다. 이번 변경에는 새 DB 작업이나 Python·프런트 의존성 설치가 필요 없다. 서버 주소와 키 설정도 바꾸지 않는다.

이전에 분석 실패로 저장된 요구사항은 수정 화면의 **AI 다시 분석**을 실행한다. 이전 분석 기록을 성공으로 임의 변경하지 않는다.

## 0건 응답 처리

`HTTP 200`과 분석 완료 상태는 별개다. 정상 검토 결과가 0건이면 확정을 진행할 수 있고, 검토하지 못한 경우는 성공 0건과 구분한다.

| AI 모델이 반환한 값 | 처리 |
|---|---|
| `{"findings":[]}` | 정상 완료, 0건 |
| `[]`, 코드 블록 안의 `[]` | 표준 빈 목록으로 정규화 |
| `{"findings":null}` | 표준 빈 목록으로 정규화 |
| 명확한 단독 무수정 문구(예: “수정할 사항이 없습니다.”, “No issues found.”) | 표준 빈 목록으로 정규화 |
| 빈 응답, `{}`, JSON 파싱 오류, 결과 목록 누락 | 동일한 전체 검토 문맥으로 구조화 응답을 한 번 더 요청 |
| 재요청도 실패하거나 모델 결과에 잘못된 위치·필수 정보가 있음 | 부분 실패로 표시, 입력 유지 |

다른 기능의 JSON 파서를 느슨하게 바꾸지 않고 요구사항 검토 응답에서만 정규화한다. 용어 추출이나 산출물 생성의 실패를 “문제 없음”으로 바꾸지 않는다. 규칙 검토의 긴 문장을 걸러냈다는 이유만으로, 이후 정상 완료한 AI 문맥 검토까지 부분 실패로 표시하지 않는다.

## 검토 화면

1. 상단의 번호별 항목을 선택한다. 선택한 한 항목의 원문 구절, 변경 이유, 해석 차이, AI 수정안을 표시한다. 이전·다음 버튼으로 이동할 수 있다.
2. 제안 아래에 화면 전체 너비로 **분석한 원문 / 확정할 최종 본문**을 비교한다. 좁은 화면에서는 본문을 위아래로 배치한다.
3. 원문에서는 검토 위치를 번호와 노란색으로 표시한다. 선택한 항목은 테두리로 추가 강조하고 두 본문에서 해당 위치로 스크롤한다.
4. 본문의 강조 구절을 누르면 해당 제안으로 이동한다. 제안의 “본문 위치 보기”로 본문 비교 영역을 찾을 수 있다.
5. **AI 제안 반영하기**를 누르면 해당 구절만 교체·앞뒤 삽입·삭제한다. 반영한 부분은 최종 본문에서 초록색으로 표시하며, 삭제는 삭제된 위치에 배지를 남긴다.
6. **직접 수정하기**를 누르면 “원문 구절을 대신할 문장” 입력창을 연다. 작성 중에는 최종 본문과 검토 결정이 바뀌지 않는다. **직접 수정한 문장 반영**을 눌러야 본문이 바뀌며 보라색으로 표시한다. 취소하면 작성한 문장만 버리고 기존에 반영한 결정은 유지한다.
7. 수정하지 않을 항목은 **원문 유지**로 결정한다. 이는 본문 수정 방식이 아니며 원문을 그대로 둔다.
8. 모든 항목을 결정한 뒤 최종 본문을 확인하고 **요구사항 확정**을 눌러 검토 결정을 저장한다. 등록·기존 확정 본문을 그대로 유지했다면 고객 합의 창 없이 바로 확정하고 이슈 단계로 이동한다. 본문을 변경했다면 고객 담당자·합의일·합의 내용·변경 요약을 입력해 확정한다.

최종 본문은 읽기 전용이다. “최종 본문 직접 수정” 체크박스는 제거했다. 서버에는 각 항목의 AI 반영·직접 수정·원문 유지 결정과, 이 결정들로 구성한 본문을 `manualContent:false`로 보낸다.

## 편집 보호와 확정 조건

- 작성 중인 직접 수정 문장은 항목을 이동해도 유지한다. 반영하거나 취소하기 전에는 재분석·확정을 막는다. 해당 항목에 “작성 중”을 표시한다.
- 반영한 결정은 현재 탭의 세션 저장소에 보관하며 동일 분석 결과를 새로고침했을 때 복원한다. 아직 반영하지 않은 직접 입력 문장은 새로고침 복원 대상이 아니다.
- 수정 위치는 UTF-16 원문 위치를 기준으로 한다. 앞부분의 길이가 바뀌어도 뒤 항목의 강조 위치를 이동한다. 반복 문장의 첫 구절을 임의 선택하지 않는다.
- 수정 범위가 겹치면 확정을 막는다. 겹친 항목 중 하나를 원문 유지로 정한 뒤 한 항목에서 수정 내용을 함께 반영한다.
- AI 부분 실패·연결 실패, 변경된 용어 정의, 미결정 항목, 작성 중 문장, 남아 있는 `⟦…⟧` 입력 표시가 있으면 확정할 수 없다.
- 본문을 변경한 상태에서 필수 상충 항목을 원문 유지로 결정했다면 고객 합의 단계에서 별도의 수용 근거를 입력한다. 본문 전체를 변경 없이 유지했다면 기존 합의 본문을 유지한 결정으로 기록하며 새 고객 합의 정보를 만들지 않는다.
- 재분석은 현재 반영된 최종 본문과 동일 프로젝트의 다른 요구사항 전체, 용어 문맥을 사용한다.

## 검증

AI 응답 정규화·재요청·실패 구분과 문맥 검토는 Python 테스트로 검사한다. 프런트 단위 검사는 원문 유지, 정확한 위치 교체, 삽입·삭제, 중첩 방지, UTF-16 위치, 수정 이후 강조 위치를 검사한다. 타입 검사와 프로덕션 standalone 빌드를 수행한다.

브라우저 검증에는 API 테스트 응답을 사용한다. 실제 사내 LLM과 Oracle 연결 상태는 별도 운영 환경에 해당한다. 실행용 패키지는 Next.js 런타임 키를 비운 상태로 저장하고 실행 시 생성한다.

## 본문 변경 여부와 합의 창 읽기

- 비교 기준은 AI 초안이 아니라 서버에 저장된 등록 원문 또는 현재 확정 본문이다. AI 제안을 적용했다가 원문으로 되돌린 경우도 최종 본문이 같으면 합의를 다시 입력하지 않는다. 줄바꿈 인코딩(CRLF/LF)만 정규화하며 문장·수치·공백의 실제 변경은 변경으로 본다.
- 최초 원문 확정은 합의 행을 임의 생성하지 않고 버전 이력의 합의 ID를 null로 저장한다. 이미 확정한 본문을 그대로 다시 확인하면 버전·작업 묶음을 새로 만들지 않아 기존 이슈·산출물·Jira 연결을 보존한다.
- AI 검토 완료, 적용·직접 수정·원문 유지 결정 저장, 최신 요구사항·용어 기준 검사는 그대로 적용한다. 고객 합의 생략이 AI 검토 생략을 의미하지 않는다.
- 본문 변경이 있어 합의 창을 여는 경우 입력란과 최종 본문을 넓게 나란히 보여준다. ‘본문 크게 보기’를 누르면 입력란을 잠시 접고 본문을 전체 너비로 펼친다. ‘합의 입력으로 돌아가기’를 눌러도 입력한 합의 내용은 유지한다.
- 본문 검색으로 문구를 강조할 수 있다. 작은 화면에서는 입력란과 본문을 한 열로 표시하며, 크게 보기에서는 본문 전체를 펼쳐 읽는다.

이번 변경에는 DB 변경이나 새 의존성 설치가 필요 없다. 백엔드와 프런트를 최신 버전으로 다시 시작한다.
