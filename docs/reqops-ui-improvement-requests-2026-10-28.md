## 2. 요구사항 상태와 Step 정리

### 사용자 요청

요구사항의 상태와 Step을 정리한 정보를 제공한다. 가능하면 `Project/id/requirement` 화면에서 현재 단계와 단계별 설명을 확인할 수 있게 한다.

사용자가 제시한 단계 예시: **등록 → 검출 → 합의 → 도출 준비**.

### 정리 방향

- **상태**: 요구사항에 저장된 업무 진행 상태. 예: 접수, 고객 합의 대기, 확정.
- **Step**: 사용자가 거치는 작업 순서와 현재 해야 할 일.
- AI 실행 상태·검토한 건수는 별도 정보다. 업무 상태나 Step과 섞어서 표시하지 않는다.
- 요구사항 상태만으로 검출 완료 여부나 고객 합의의 실제 진행 상황을 단정하지 않는다.

### Step 안내 제안

아래는 화면 안내를 위한 제안이며, 현재 코드의 확정된 상태 매핑이 아니다.

| Step | 의미 | 화면에서 알려줄 내용 |
|---|---|---|
| 등록 | 요구사항을 입력하고 저장 | 등록 여부, 저장한 본문 |
| 검출 | AI 검토 결과를 확인하고 본문 수정 | 검토 실행 여부, 검출 내용, 재검토 필요 여부 |
| 합의 | 검토한 본문과 미해결 항목에 대해 고객과 합의 | 합의 기록 유무, 다음 행동 |
| 도출 준비 | 합의한 요구사항을 확정하고 개발 이슈 도출 준비 | 확정 여부, 도출 가능 여부와 미충족 조건 |

## 3. 수정 화면의 AI 검토 UI 정리 및 결과 미표시 확인

### 사용자 관찰

`requirements/id/edit`의 핵심 흐름은 **검출 → 수정 → 요구사항 확정**인데, 보조 정보가 많아 무엇을 해야 하는지 알기 어렵다.

혼란을 주는 항목:

- 추가검토요청
- 부분검토
- 기존요구사항 6/6건 AI검토
- AI가 확인하고 싶은 내용

또한 **AI가 검토한 내용이 화면에서 보이지 않는다**는 문제가 있다.

### 조사·정리할 내용

| 항목 | 확인할 내용 | 정리 방향 |
|---|---|---|
| 추가검토요청 | 추가 검토의 대상·실행 조건·다른 재검토 기능과의 차이 | 중복 기능 통합, 필요한 경우 대상과 목적을 명확하게 표시 |
| 부분검토 | 일부 요구사항만 검토했는지, 호출 실패인지, 별도 검토 방식인지 | 미검토 범위와 원인, 다음 행동을 표시 |
| 기존요구사항 6/6건 AI검토 | 비교 대상 수인지, 실제 성공 수인지, 상세 결과로 연결되는지 | 개수의 의미와 결과 확인 경로를 제공 |
| AI가 확인하고 싶은 내용 | 검출 결과·등록 질문·추가 확인 질문의 관계 | 중복을 줄이고 질문의 이유와 대상 본문을 연결 |
| 검토 결과 미표시 | 결과 생성·저장·조회·화면 표시 중 어느 단계에서 누락되는지 | 원인을 확인한 후 실제 결과를 조회할 수 있도록 수정 |

### AI 결과 미표시 조사 체크리스트

- [ ] 동일 요구사항에서 문제를 재현하고 실행 시점·본문 버전·요청 ID를 확인한다.
- [ ] AI 응답에 검토 결과가 있는지 확인한다.
- [ ] 결과가 서버에 저장되고 조회 API로 반환되는지 확인한다.
- [ ] 프론트의 필드 매핑·필터·접힘 상태·표시 조건을 확인한다.
- [ ] 최초 검토와 재검토 결과가 서로 잘못 대체되거나 이전 결과로 남는지 확인한다.
- [ ] 발견 없음, 결과 로딩 중, 실패, 일부 미검토, 이전 본문 기준 결과를 구분한다.

위 항목은 조사 계획이다. 현재 원인이나 재현 성공을 단정하지 않는다.

### 완료 기준

- [ ] 사용자는 검출 결과 확인, 본문 수정, 확정 순서를 쉽게 따라갈 수 있다.
- [ ] AI 검토 항목의 문제 문장·이유·수정 제안을 확인할 수 있다.
- [ ] 검토 건수만 표시되고 실제 내용은 확인할 수 없는 상태를 해소한다.
- [ ] 세부 실행 정보가 핵심 작업을 가리지 않는다.
- [ ] 같은 의미의 질문·재검토 버튼·상태 안내가 중복되지 않는다.

## 4. 공통 사이드 챗봇 방식의 AI 재검토 제안

### 사용자 제안

페이지마다 AI 재검토 컴포넌트를 반복해서 만드는 대신, **화면 옆 공통 챗봇 영역**에서 요청하고 결과를 확인하는 방식을 검토한다.

AI API에는 **현재 열려 있는 페이지의 문맥 + 사용자의 요청**을 전달하고, 페이지와 작업에 맞는 프롬프트를 적용한다.

### 설계 제안

- 공통 사이드 패널에서 질문·재검토 요청·결과 이력을 제공한다.
- 페이지별로 UI를 복제하는 대신, 페이지 문맥과 작업별 프롬프트 설정을 분리한다.
- 사용자가 어떤 프로젝트·요구사항·본문을 대상으로 질문하는지 패널에 표시한다.
- 수정 화면에서는 저장된 본문과 현재 편집 중 본문을 구분한다.
- 검토 결과는 해당 요구사항·본문 버전과 연결해 다시 열어도 확인할 수 있게 한다.
- 다른 페이지로 이동하면 이전 대화와 현재 작업 대상이 혼동되지 않게 한다.
- 챗봇 응답을 본문에 반영하거나 요구사항을 확정하는 동작은 사용자의 명시적 조작으로 연결한다.

### 문맥·프롬프트 구성 예시

아래 필드는 설계 예시이며, 현재 API의 필드명이나 구현된 계약을 뜻하지 않는다.

| 구분 | 전달할 내용 |
|---|---|
| 페이지 문맥 | 현재 경로, 페이지 종류 |
| 작업 대상 | 프로젝트 ID, 요구사항 ID, 상태, Step, 본문 버전 |
| 검토 입력 | 현재 편집 본문, 비교에 필요한 기존 요구사항과 이전 검토 결과 |
| 사용자 요청 | 사용자가 입력한 질문·추가 검토 지시 |
| 프롬프트 설정 | 페이지·작업별 목적, 검토 기준, 응답 형식 |

| 페이지 | 프롬프트 목적 예시 |
|---|---|
| 프로젝트 상세 | 프로젝트 현황과 다음 작업 설명 |
| 요구사항 목록 | 상태·Step 설명과 검토할 요구사항 안내 |
| 요구사항 수정 | 현재 본문 검토, 검출 이유 설명, 사용자 요청을 반영한 재검토 |
| 산출물 | 개발 이슈와 연결 이슈의 관계·현황 설명 |

### 검토·완료 기준

- [ ] 공통 사이드 챗봇의 도입 여부와 기존 AI UI의 통합 범위를 결정한다.
- [ ] 도입 시 현재 페이지와 사용자 요청에 맞는 프롬프트로 API를 호출한다.
- [ ] 검토 결과를 대상 본문과 연결하고, 본문 변경 후에는 이전 결과임을 구분한다.
- [ ] 공통 챗봇으로 이동하더라도 검출 결과 확인·본문 수정·고객 합의·확정 동선이 유지된다.

## 6. 산출물 탭 접근 문제 및 산출물 정의 정리

### 사용자 관찰

요구사항 상태가 **접수**, **고객 합의 대기**일 때 산출물 영역에서 열리지 않는 탭이 있다. 정확한 탭명·클릭 동작·오류는 재현 시 확인한다.

### 산출물의 정의

이 요청에서 산출물은 다음을 의미한다.

1. **요구사항에서 도출된 개발 이슈**
2. **해당 개발 이슈에 역방향으로 연결되는 이슈**

요구사항 자체를 산출물 목록으로 취급하지 않는다. 역방향 연결은 링크의 방향과 관계 유형을 확인해 표현하며, 구체적인 관계 유형·탐색 깊이는 실제 Jira 연결 구조를 확인한 뒤 정리한다.

### 조사·수정 방향

- 접수·고객 합의 대기 상태에서 탭 클릭을 재현한다.
- 프론트의 탭 비활성화 조건, 라우팅, API 호출, 서버의 상태 제한을 확인한다.
- **산출물 조회 가능 여부**와 **신규 산출물 도출 가능 여부**를 구분한다.
- 신규 도출의 선행 조건 때문에 이미 연결된 이슈의 조회까지 막고 있는지 확인한다.
- 도출 전이라 이슈가 없다면 빈 상태와 다음 행동을 안내한다.
- 개발 이슈에서 원래 요구사항을 확인하고, 역방향 연결 이슈는 원래 이슈와의 관계를 확인할 수 있게 한다.

### 완료 기준

- [ ] 접수·고객 합의 대기 상태에서 각 탭의 접근 동작을 확인한다.
- [ ] 탭을 열 수 없는 원인을 확인하고 의도하지 않은 접근 제한을 수정한다.
- [ ] 도출 불가·연결 이슈 없음·조회 실패를 구분해서 표시한다.
- [ ] 개발 이슈와 역방향 연결 이슈의 키·제목·상태·관계·이동 링크를 확인할 수 있다.
- [ ] 요구사항 상태와 Jira 개발 이슈 상태를 혼동하지 않게 표시한다.

## 후속 작업 순서 제안

1. 상태·Step·산출물의 의미와 실제 조건을 확인한다.
2. AI 결과 미표시와 산출물 탭 접근 문제를 재현하고 원인을 확인한다.
3. Active Flow 제거와 프로젝트 Jira 링크 표시를 반영한다.
4. 공통 사이드 챗봇 도입 범위를 결정하고 AI 검토 UI를 정리한다.
5. 상태별 화면 접근과 검토 결과 조회를 검증하고 문서를 갱신한다.

## 문서 확인 범위

이 문서는 사용자 요청과 `semes` 브랜치의 README, 요구사항 상태 명세서, 요구사항 검토 사용 안내를 참고해 작성했다. 서비스 실행, 실제 DB·Jira·사내 AI API 연결, 최신 코드 전체 대조는 수행하지 않았다. 따라서 장애 원인과 기존 문서의 상태 전이 설명은 후속 구현에서 검증해야 한다.

## 7. 도출 이후 재진입·검토·전체 확정 흐름 (추가 요청)

### 보고된 문제

- 개발 이슈와 산출물을 이미 도출했는데 뒤로가기로 3단계에 돌아오면 다시 `이슈 확정 및 산출물 4종 자동 생성` 버튼이 나온다.
- 4단계에서 `16/16 생성`으로 표시돼도 개발 이슈와 각 산출물을 열 수 없다.
- `Jira 이슈 생성 후 열기`가 비활성화돼 원인을 알기 어렵다.
- 전체 확정 후 안내 문구와 버튼만 바뀌며, 재진입하면 다시 3단계로 돌아간다.

### 적용 내용

- 기존 개발 이슈가 있으면 3단계 진입 시 4단계 검토 화면으로 연결한다. 조회 과정에서 재생성을 실행하지 않는다.
- 개발 이슈·산출물 이름을 실제 상세 조회 링크로 변경하고 상세 화면을 구현했다. 상세 화면에서 검토 목록으로 돌아갈 수 있다.
- 전체 확정 완료 화면에 확정 상태와 프로젝트 산출물 목록 이동 링크를 제공한다. 다시 들어와도 저장된 묶음 상태를 조회한다.
- Jira 등록 버튼의 비활성화 이유를 표시한다. 대상 미설정, 유형 ID 미설정, 생성 미완료, 산출물 누락을 구분한다. 이미 연결한 Jira 이슈는 직접 열 수 있다.

## 이번 구현 및 실행 안내

- 프로젝트 상세 Active Flow 제거, 프로젝트 정보에 Jira 링크 표시.
- 요구사항 목록에 등록·검출·합의·도출 준비 안내와 상태 설명 추가.
- AI 검토 결과 비교 영역을 기본으로 펼치고, 추가 질문은 별도 접이 영역으로 정리.
- 모든 프로젝트 화면에서 공통 AI 도우미 패널 제공. 현재 페이지·대상 요구사항·사용자 요청·최근 대화를 전송한다. 편집 페이지는 미저장 본문도 전달한다.
- AI 도우미의 `현재 본문으로 정식 재검토`는 기존 재검토 API에 입력한 요청을 전달한다. 일반 대화는 수정·확정 작업을 실행하지 않는다.
- 대화 이력은 현재 페이지를 떠나면 초기화된다. 정식 검토 결과는 기존 서버 저장 방식을 사용한다.
- 산출물 목록은 실제 개발 이슈를 표시하며 원본 요구사항 상태와 관계없이 기존 이슈를 조회한다. 이슈가 없다면 검토·확정 또는 도출로 이동한다.
- 개발 이슈 상세와 4단계에서 Jira의 직접 역방향 연결(inwardIssue)을 조회한다. 재귀 탐색은 하지 않는다. 인증 미설정·조회 실패는 빈 결과와 구분한다.
- DB 스키마 변경 없음. 백엔드·AI 서버를 업데이트해 재시작하고 새 프론트 배포 패키지를 사용한다. 기존 모델 연결 설정과 Jira 인증 설정을 사용한다.

### 검증과 한계

- AI 서버 테스트 71건 통과(공통 AI 프롬프트·본문 문맥·연결 미설정 처리 포함).
- 프론트 단위 검사 14건과 라우트 검사 1건 통과.
- 백엔드 테스트는 Maven Central DNS 연결 실패로 의존성을 받지 못해 실행하지 못했다.
- 실제 Oracle DB, 사내 LLM, Jira 서버 연동은 이 환경에서 검증하지 못했다. Jira 버튼이 활성화되더라도 실제 인증·권한 문제는 서버의 오류 안내를 확인해야 한다.
- 프론트 프로덕션 빌드·타입 검사와 standalone 패키징 완료. `frontend/dist/standalone`에 실행 패키지를 갱신했다.
- 브라우저 동선 검증은 Chromium 다운로드 실패로 실행하지 못했다. 라우트 검사는 실제 브라우저 클릭 검증을 대체하지 않는다.
