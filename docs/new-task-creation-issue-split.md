# 신규 태스크 생성 기준: 개발 이슈 분할안과 프롬프트

## 1. 개발 이슈를 어떻게 나눌까?

**개발 이슈 2개**가 적합하다. 외부 시스템의 이벤트 수신과 권한 있는 사용자의 수동 생성은 각각 별도로 시작하고 별도로 완료를 검증할 수 있다. 반면 메시지 형식은 이벤트 생성에 필요한 계약이고, 권한·입력 제약·실적 미보고는 수동 생성의 동작 조건이다. 문장이나 제약마다 티켓을 만들면 하나의 생성 경로를 완성하기 위해 여러 이슈를 동시에 완료해야 한다.

| 이슈 | 구현 범위 | 완료를 확인하는 방법 | 대표 원문 근거 |
| --- | --- | --- | --- |
| 1. 외부 이벤트 수신을 통한 태스크 생성 | 외부 시스템과 주고받을 **신규 태스크 생성 메시지 형식**을 정의하고, 그 형식의 이벤트를 수신하여 필요한 데이터를 해석하고 태스크를 생성한다. | 합의된 형식의 이벤트를 수신하면 그 정보로 신규 태스크가 생성된다. 메시지 형식에 맞지 않는 입력의 처리 기준은 계약 확정 후 시험한다. | “외부 시스템으로부터 약속된 형식의 이벤트 메시지를 수신 받아 신규 태스크를 생성한다.” / “신규 태스크 생성을 위한 메시지 형식을 정의한다.” |
| 2. 최상위 권한 계정의 수동 태스크 생성 | 사용자 메뉴의 입력 항목과 상세 제약(동일 자재 ID로 여러 태스크 생성 허용 여부 포함)을 정의한다. 최상위 권한 계정만 생성할 수 있게 하고, 수동 생성 시 자재·설비 상태 등 수행 조건은 확인된 것으로 간주하며, 해당 태스크의 전개와 실적은 외부 시스템에 별도 보고하지 않는다. | 최상위 권한 계정은 정의된 입력과 제약에 따라 생성할 수 있고 그 외 계정은 생성할 수 없다. 수동 생성 태스크에는 지정된 사전 확인 가정을 적용하고 전개·실적에 대한 별도 외부 보고가 발생하지 않는다. | “사용자 메뉴를 통해 필요한 정보를 입력받아 신규 태스크를 생성한다.” / “사용자 메뉴를 통해 생성된 태스크의 전개와 실적은 외부 시스템에 별도 보고하지않는다.” |

두 경로에서 쓰는 **태스크 저장과 생성 처리**는 공통 서비스로 구현할 수 있다. 이것만 별도 개발 이슈로 분리할지는 기존 구현이 이미 있는지와 독립적인 완료 결과가 있는지를 본 뒤 결정한다. 현재 원문만으로는 세 번째 고객 기능으로 세지 않는다.

### 설계 전에 확정해야 할 사항

- 외부 이벤트의 필수 필드, 식별자, 유효성 검사, 같은 이벤트의 재수신 처리, 응답·오류 방식은 명시되지 않았다. 실제 메시지 형식은 관계자와 합의해 이슈 1의 계약으로 확정한다.
- 수동 입력 필드와 동일 자재 ID의 복수 태스크 허용 여부는 **정의하라는 요구**일 뿐, 구체적인 허용·금지 정책은 주어지지 않았다. AI가 임의로 정하지 않는다.
- “최상위 권한”이 가리키는 실제 역할·권한 식별자를 확인해야 한다. 메뉴 숨김과 함께 생성 요청에 대한 서버 권한 검사도 이슈 2의 범위다.
- 수동 생성의 “조건이 확인된 것으로 간주”하는 범위와 태스크 생성에 필요한 공통 무결성 검사 범위를 구분해 확정해야 한다. 모든 검사를 무조건 생략하라는 뜻으로 확대하지 않는다.
- “외부 시스템에 별도 보고하지 않는다”는 **수동 생성 태스크의 전개·실적**에만 명시된 규칙이다. 외부 이벤트로 생성된 태스크의 보고 방식은 이 원문에서 결론 내리지 않는다.

> 아래 인용은 사용자가 제공한 원문의 대표 구절이다. 원문의 문장이 이슈별로 모여 있지 않으므로, 각 이슈의 근거는 표처럼 여러 구절에 흩어져 있다.

## 2. 변경 전 이슈 분할 프롬프트 (기록)

2026-11-24 변경 전 `ai-model/main.py`에 있던 `_SPLIT_SYSTEM_PROMPT` 전문이다. 현재 실행 중인 프롬프트는 아래 3절과 `PROMPTS.md`를 참고한다. 사용자 메시지는 `요구사항: {확정 본문}`에 선택적으로 `참고 지시: {입력 내용}`과 기존 요구사항 문맥을 덧붙인다.

```text
당신은 반도체 장비 소프트웨어(VCS/AMR) 요구사항을
독립적으로 구현·검증할 수 있는 개발 이슈(Jira 티켓)로 묶는 전문가다.
먼저 요구사항 전체의 업무 목표와 최종 결과를 파악하고, 기본적으로 이슈 1개로 본다.

분할 기준:
- 서로 다른 업무 결과를 제공하고, 각각 독립적으로 구현·시험·완료할 수 있을 때만 나눈다.
  기능 이름, 모듈, 클래스, 문장, 화면, 처리 순서가 다르다는 이유만으로 나누지 않는다.
- 같은 업무 결과를 완성하는 입력 조건, 후보 필터, 우선순위, 계산식, 동률 처리,
  상태 전이, 예외, 재시도, 설정값은 하나의 이슈에 포함한다. 그중 하나만 구현해서는
  업무 결과가 완성되지 않는다면 반드시 묶는다.
- 예: 가용 AMR 조건(IDLE/Auto/SOC), 맨해튼 거리, 동률 우선순위, 알람 시 재할당이
  한 가지 'AMR 할당' 동작을 정의한다면 'AMR 할당 기준 및 예외 처리' 이슈 하나다.
  단순히 조건이 여러 문장에 적혀 있다는 이유로 별도 이슈로 만들지 않는다.
- 정말 독립된 결과가 여러 개일 때만 복수 이슈를 만든다. 분리할 근거가 애매하면
  이슈 1개로 두고 전체 요구사항을 그 이슈에 포함한다.
- 각 quote는 해당 이슈의 조건·예외까지 포함하는 원문의 연속된 구절을 그대로 쓴다.
  한 이슈로 묶어야 하는 문장들이 떨어져 있어 연속 구절로 나타낼 수 없다면
  요구사항 전체를 이슈 1개로 둔다. 원문에 없는 표현이나 중복 quote는 사용하지 않는다.
- title은 구현할 업무 결과가 드러나도록 간결하게 쓴다.

반드시 아래 JSON 형식으로만 답한다.
{"issues":[{"title":"이슈 제목","quote":"원문 그대로의 해당 구절"}]}
```

### 변경 전 프롬프트에서 걸렸던 지점

첫 번째 기준인 “독립적으로 완료할 수 있는 업무 결과”를 적용하면 외부 이벤트 생성과 수동 생성은 분리된다. 그러나 마지막의 **연속된 구절** 규칙은 동일 이슈에 속하는 문장들이 떨어져 있으면 요구사항 전체를 한 이슈로 만들라고 한다. 이 사례에서는 두 경로에 관한 세부 규정이 서로 떨어져 있으므로, 이 규칙이 업무 결과 기준보다 우선 적용되면 한 이슈로 합쳐질 수 있다. 실제 모델의 응답을 실행해 확인한 결과는 아니며, 프롬프트 규칙을 읽고 예상한 충돌이다.

## 3. 코드에 반영한 이슈 분할 프롬프트

아래 프롬프트를 `semes` 브랜치의 `ai-model/main.py`에 있는 `_SPLIT_SYSTEM_PROMPT`에 반영했다. 현재 `POST /split`의 `title`, `quote` JSON 형식을 유지한다. 위의 원문 전체를 사용자 메시지의 `{확정 요구사항 본문}` 자리에 넣어 사용할 수 있다. AI 서버를 재시작하면 변경된 프롬프트가 사용된다.

### 시스템 프롬프트

```text
당신은 VCS/AMR 요구사항을 독립적으로 구현하고 검증할 수 있는 개발 이슈(Jira 티켓)로 나누는 전문가다.
요구사항의 전체 목적과 결과를 먼저 파악한 뒤, 구현을 마쳤을 때 따로 검증할 수 있는 업무 결과를 찾는다.

분할 원칙:
1. 기본값은 이슈 1개다. 서로 다른 시작점과 업무 결과가 있고, 각 결과를 독립적으로 구현·시험·완료할 수 있을 때만 분리한다.
2. 외부 이벤트 수신을 통한 생성과 사용자 메뉴를 통한 수동 생성처럼 진입 경로, 권한 또는 외부 연동 책임, 결과 확인 방법이 달라 각각 완료할 수 있다면 별도 이슈로 만든다.
3. 한 경로를 완성하기 위한 메시지 형식, 입력 필드, 입력 제약, 권한, 상태 확인 가정, 외부 보고 여부는 그 경로의 이슈에 포함한다. 문장 수·화면 수·클래스 수만으로 분리하지 않는다.
4. 서로 떨어져 있는 문장도 같은 경로의 조건이라면 같은 이슈에 포함한다. 원문 순서가 섞여 있다는 이유로 독립된 두 결과를 한 이슈로 합치지 않는다.
5. 각 이슈의 quote에는 그 경로를 가장 잘 대표하는 원문의 연속된 구절 하나를 글자 그대로 넣는다. quote가 하나라고 해서 떨어진 다른 조건을 이슈 범위에서 빼지 않는다. 원문에 없는 구절을 만들거나 서로 다른 구절을 이어 붙이지 않는다.
6. 태스크 저장 같은 공통 내부 구현을 고객에게 독립된 결과로 확인받는 별도 기능처럼 추가하지 않는다.
7. 정의가 필요하다고만 적힌 필드·중복 허용 정책·메시지 값·오류 처리·보고 정책은 임의로 확정하지 않는다. 명시된 수동 생성의 미보고 조건을 외부 이벤트 생성까지 확대하지 않는다.
8. title은 구현할 업무 결과가 보이게 간결하게 작성한다. 원문에 두 결과가 없으면 억지로 2개를 만들지 않는다.

JSON만 반환한다. 설명이나 코드 블록을 붙이지 않는다.
{"issues":[{"title":"구현할 업무 결과","quote":"원문에 실제 등장하는 연속된 대표 구절"}]}
```

### 사용자 메시지 예시

```text
요구사항: {확정 요구사항 본문}
참고 지시: 각 이슈에서 전체 원문의 관련 조건과 예외를 함께 고려하고, 서로 다른 생성 경로가 독립적으로 완료 가능한지 판단하라.
```

### 이 사례에 기대하는 응답의 형태

```json
{
  "issues": [
    {
      "title": "외부 이벤트 기반 신규 태스크 생성",
      "quote": "외부 시스템으로부터 약속된 형식의 이벤트 메시지를 수신 받아 신규 태스크를 생성한다."
    },
    {
      "title": "관리자 메뉴의 수동 태스크 생성",
      "quote": "사용자 메뉴를 통해 필요한 정보를 입력받아 신규 태스크를 생성한다."
    }
  ]
}
```

`quote`는 대표 구절 하나이므로 위 JSON만으로는 각 이슈의 **흩어진 다른 근거**를 저장하거나 누락 여부를 자동 검증할 수 없다. 실제 구현 범위에는 이 문서 1절의 다른 근거도 반드시 포함해야 한다. 여러 근거를 시스템적으로 추적하려면 응답·저장 모델에 `evidenceQuotes[]` 같은 복수 인용 필드를 추가하고, 각 인용이 원문에 있는지와 어떤 이슈에 연결되는지 검증하는 별도 변경이 필요하다. 이번 변경은 분할 프롬프트만 실제 코드에 반영했다. 복수 인용 저장·검증을 위한 API나 데이터 모델 변경은 포함하지 않는다.
