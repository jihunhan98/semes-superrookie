# Bitbucket Server 연동으로 도메인 지식 추출하기 — 가능성 검토 및 구현안

> 요청 배경: `bit-stms.semes.com:17990`(Bitbucket Server/Data Center, 포트로 보아 자체 커스텀 배포)에서
> 관리 중인 레포의 브랜치·코드를 API로 가져와서, AI가 그 코드를 읽고 "도메인 지식"(VCS/AMR
> 반도체 장비 소프트웨어의 실제 구조·컨벤션·용어)을 추출해 프롬프트에 반영하고, 나중에 요구사항
> 검토·산출물 도출 시 실제 코드를 참고해서 더 정확하게 분석하게 만들고 싶다는 아이디어.
>
> **주의**: 이 문서는 이 세션(클라우드 격리 환경)이 인터넷은 되지만 `bit-stms.semes.com`은 사내
> 폐쇄망 주소라 DNS조차 안 풀려서 직접 접속해 검증하지 못한 상태로 작성했습니다. Bitbucket
> Server REST API 자체는 수년간 안정적으로 유지된 잘 알려진 스펙이라 아래 내용은 신뢰도가
> 높지만, **실제 사내망에서 정확한 버전(`/rest/api/1.0` 이 맞는지)과 인증 방식만은 실제
> 인스턴스에 한 번 붙여서 확인**해야 합니다.

## 1. 구현 가능성 — 가능, 다만 전제조건 있음

Bitbucket Server(구 Stash)는 Bitbucket Cloud와 별개의 제품이고, REST API도 다릅니다.
`:17990` 처럼 포트를 명시한 것으로 보아 Bitbucket **Server/Data Center**(자체 호스팅판)가
맞을 겁니다 — Cloud였다면 `bitbucket.org`를 썼을 거고, Server 기본 HTTP 포트가 `7990`인데
`17990`은 사내에서 임의로 재배치한 값으로 보입니다.

가능성 자체는 높습니다:

- REST API가 코드 조회·브랜치 목록·파일 raw 다운로드·전체 아카이브 다운로드까지 다 지원합니다.
- 인증은 Personal Access Token(Bearer) 방식이 있어서, 서비스 계정 하나로 백엔드가 정기적으로
  호출하게 만들기 쉽습니다.
- 이미 이 프로젝트 백엔드(Spring)가 `RestClient`로 외부(ai-model)를 호출하는 구조가 있어서,
  같은 패턴을 하나 더 추가하는 정도의 작업입니다.

전제조건(먼저 확인해야 할 것):

1. **네트워크 도달성** — 이 앱이 배포되는 서버(폐쇄망)에서 `bit-stms.semes.com:17990`으로
   실제 HTTP 요청이 나가는지. 사내 방화벽/사설 IP 대역이 갈리면 안 될 수도 있습니다.
2. **계정/권한** — 이 레포들을 읽을 서비스 계정(또는 개인 계정의 Personal Access Token)을
   발급받을 수 있는지, 그리고 "읽기 전용"으로 충분한지.
3. **사내 정책** — 사내 소스코드를 (사내망 LLM이라도) AI에 통째로 넘겨 분석시키는 것에 대한
   보안/데이터 취급 정책이 있는지. 이미 사내 LLM을 쓰고 있어서 외부로 나가는 건 아니지만,
   "소스코드를 LLM에 입력값으로 쓴다"는 것 자체를 허용하는지는 별도 확인이 필요합니다.

## 2. Bitbucket Server REST API — 실제로 쓸 엔드포인트

Base: `http://bit-stms.semes.com:17990/rest/api/1.0`

| 목적 | 엔드포인트 | 비고 |
|---|---|---|
| 프로젝트의 레포 목록 | `GET /projects/{projectKey}/repos` | |
| 브랜치 목록 | `GET /projects/{projectKey}/repos/{repoSlug}/branches` | 페이지네이션(`start`/`limit`) 있음 |
| 파일/디렉터리 목록(트리 탐색) | `GET /projects/{projectKey}/repos/{repoSlug}/browse/{path}?at=refs/heads/{branch}` | `path` 생략하면 루트 |
| 파일 원문 | `GET /projects/{projectKey}/repos/{repoSlug}/raw/{path}?at=refs/heads/{branch}` | 텍스트 그대로 옴 |
| 브랜치 전체를 zip/tar로 | `GET /projects/{projectKey}/repos/{repoSlug}/archive?at=refs/heads/{branch}&format=zip` | 파일 하나하나 부르지 않고 한 번에 통째로 받을 때 |
| 커밋 이력 | `GET /projects/{projectKey}/repos/{repoSlug}/commits?until=refs/heads/{branch}` | 커밋 메시지·작성자 |
| 커밋별 변경 파일(diff) | `GET /projects/{projectKey}/repos/{repoSlug}/commits/{commitId}/diff` | |

인증: `Authorization: Bearer <Personal Access Token>` 헤더 하나로 끝. (Bitbucket Server
5.5+ 기준. 그보다 오래된 버전이면 HTTP Basic auth로 대체.) 토큰은 Bitbucket 웹 UI의
"개인 설정 → HTTP access tokens"에서 발급합니다 — 레포별로 읽기 권한만 주는 것도 가능합니다.

예시(브랜치 목록 조회):

```bash
curl -H "Authorization: Bearer <TOKEN>" \
  "http://bit-stms.semes.com:17990/rest/api/1.0/projects/VCS/repos/amr-controller/branches"
```

## 3. 구현 방안

### 3.1 전체 그림

```
[Bitbucket Server]
      │  (1) 브랜치/코드 조회 (REST API, PAT 인증)
      ▼
[Spring backend: BitbucketSyncService]  ──(2) 파일 필터링(.java/.py/.xml 등, 테스트·생성코드 제외)
      │
      ▼
[사내 LLM]  ──(3) "이 코드에서 도메인 지식을 추출해줘" 프롬프트로 요약
      │
      ▼
[DB: domain_knowledge 테이블]  ──(4) 프로젝트별 도메인 지식 문서로 저장
      │
      ▼
[기존 프롬프트(PROMPTS.md)]  ──(5) 분할/산출물 도출/검토 프롬프트에 "참고 도메인 지식" 섹션으로 주입
```

### 3.2 단계별 구현

**1단계 — 코드 가져오기 (`BitbucketSyncService`)**
- 프로젝트 설정 화면에 "Bitbucket 연동" 항목 추가: 프로젝트 키, 레포 slug, 브랜치, 토큰(암호화
  저장, `settings.json`처럼 평문 커밋되면 안 됨 — DB 컬럼 암호화 또는 환경변수).
- 최초엔 `archive` 엔드포인트로 브랜치 전체를 zip으로 받는 게 제일 간단합니다(파일 하나씩
  `browse`로 순회하는 것보다 API 호출 수가 훨씬 적음). 받은 zip을 서버 임시 디렉터리에 풀고,
  확장자 화이트리스트(`.java .py .xml .yml .sql` 등)로 필터링 + `build/`, `node_modules/`,
  테스트 코드, 생성된 코드(`*Generated*`, `target/`) 제외.

**2단계 — 도메인 지식 추출 (LLM 요약)**
- 레포가 크면 파일을 통째로 LLM에 넣을 수 없습니다. 의미 단위(클래스/모듈)로 잘라서 여러 번에
  나눠 "이 코드가 다루는 업무 개념·용어·불변조건이 뭔지 3~5줄로 요약해줘"를 반복 호출하고,
  그 요약들을 다시 한 번 종합(map-reduce 패턴)해서 최종 "도메인 지식 문서" 하나로 압축합니다.
- 출력 형식은 자유 텍스트보다 구조화된 형태(예: `{ "용어집": [...], "핵심 컴포넌트": [...],
  "제약조건": [...] }`)로 강제하면 나중에 프롬프트에 끼워 넣기 쉽고, 사람이 검토하기도 쉽습니다.

**3단계 — 저장 및 갱신**
- `domain_knowledge(project_id, source_repo, source_branch, content_json, extracted_at)` 테이블
  하나 추가. 프로젝트당 최신 1건만 유지하거나, 버전처럼 쌓아서 "언제 이 지식이 갱신됐는지"도
  같이 남기면 좋습니다(코드가 바뀌면 도메인 지식도 낡아지므로).
- 갱신 트리거는 처음엔 "설정 화면에서 수동으로 '다시 추출' 버튼" 정도로 시작하고, 나중에
  스케줄러(예: 매주 1회) 또는 Bitbucket 웹훅(push 이벤트) 연동으로 자동화하면 됩니다.

**4단계 — 기존 프롬프트에 주입**
- `PROMPTS.md`의 분할(`_SPLIT_SYSTEM_PROMPT`)·산출물 도출·검토 프롬프트 앞에 "참고 도메인
  지식" 섹션을 추가하고, 해당 프로젝트의 `domain_knowledge.content_json`을 요약해서 끼워
  넣습니다. 문서가 너무 길면 프롬프트가 비대해지니, 이번에도 "요구사항 본문과 관련 있어
  보이는 부분만 골라내는" 간단한 키워드 매칭 정도로 시작하는 게 현실적입니다(임베딩 기반
  RAG는 이후 확장으로 미루는 게 안전 — 아래 5절 참고).

## 4. 리스크 / 확인해야 할 것

| 리스크 | 완화 방법 |
|---|---|
| 네트워크 도달 불가 | 실제 배포 서버에서 `curl`로 먼저 확인. 안 되면 이 기능 자체가 성립 안 함 |
| 토큰 유출 | DB 암호화 컬럼 또는 Vault류 사용, 절대 `git`에 커밋 금지 |
| 레포가 너무 커서 LLM 비용/시간 폭증 | 확장자·경로 화이트리스트로 먼저 줄이고, map-reduce 요약 |
| 코드가 바뀌었는데 도메인 지식이 낡음 | 갱신 시각을 화면에 노출, 수동 재추출 버튼 필수로 제공 |
| 사내 코드를 LLM 입력으로 쓰는 것 자체의 정책 문제 | 구현 전에 반드시 확인 — 이건 기술 문제가 아니라 승인 문제 |

## 5. 추가 아이디어 확장

- **요구사항 ↔ 코드 추적성 연결**: 커밋 메시지나 브랜치명에 `REQ-1042` 같은 요구사항 키를
  적는 컨벤션을 사내에서 쓰고 있다면(또는 앞으로 쓰기로 하면), 커밋 이력 API로 그 키를
  검색해서 "이 요구사항이 실제로 어떤 커밋/파일 변경으로 이어졌는지"를 자동으로 연결할 수
  있습니다. 지금 사이드바에 이미 자리만 잡혀 있고 아직 기능이 없는 **"추적성"** 메뉴가 바로
  이 용도로 쓰기 좋은 자리입니다.
- **커밋 diff를 검토 AI의 참고자료로**: 도메인 지식(정적 요약)뿐 아니라, 최근 커밋들의 diff를
  "최근에 실제로 뭐가 바뀌고 있는지"의 신호로 검토 프롬프트에 곁들이면, "이 요구사항이 이미
  구현 중인 것과 충돌하는지" 같은 판단에 도움이 될 수 있습니다.
- **모듈-요구사항 카테고리 매핑**: 도메인 지식 추출 시 "이 클래스/모듈은 어떤 업무 영역
  (예: AMR 배터리, 경로 탐색, 충전 스테이션)을 다루는지" 태깅해두면, 다음에 비슷한 요구사항이
  들어왔을 때 "영향 범위"를 AI가 먼저 추천해줄 수 있습니다(Detail Design의 Class Diagram
  초안을 실제 클래스 이름으로 미리 채워주는 것도 가능해집니다).
- **Detail Design 산출물의 실제 코드 검증**: 지금 Class Diagram은 AI가 지어내는 목업인데,
  도메인 지식에 실제 클래스 목록이 있으면 "이 이름이 실제로 존재하는 클래스인지" 정도의
  가벼운 검증(존재하지 않으면 경고)도 나중에 가능합니다.

# 아이디어 5 — 이슈(개발 이슈) 버전별 변경 히스토리 UI/UX

## 요청 요약

요구사항이 v1.0.0 → v1.0.1 → … → v1.0.3 처럼 여러 번 재확정될 때, 그때마다 "개발 이슈 나누기"도
다시 실행되면서 이슈가 추가/삭제/제목 변경될 수 있습니다. 지금은 재확정할 때마다 이슈 목록이
통째로 새로 만들어지고 이전 상태는 사라져서, "이 이슈가 버전이 올라가면서 어떻게 바뀌었는지"를
한눈에 볼 방법이 없습니다. 이걸 볼 수 있게 해달라는 요청입니다.

## 지금 데이터 구조상 필요한 선행 작업

지금 `DevIssue`는 요구사항당 "현재 상태"만 저장하고(재확정 시 `deleteByRequirementId` 후
다시 insert), 어느 버전에서 만들어졌는지 기록이 없습니다. 이 기능을 만들려면 먼저:

- `dev_issues`에 `requirement_version_id`(또는 `version` 문자열) 컬럼을 추가해서, "이 이슈가
  어느 확정 버전 시점의 것인지"를 남겨야 합니다.
- 재확정 시 기존 이슈를 지우지 않고, 새 버전용 이슈 세트를 별도로 추가 저장(버전별로 쌓기)하는
  방식으로 바꿔야 합니다. — 이건 이번 UI 리팩토링 범위를 벗어나는 **백엔드 스키마 변경**이라
  별도 작업으로 다뤄야 합니다(코드 변경 전에 먼저 논의가 필요합니다).

## 예상 UI/UX — 와이어프레임

버전 이력 화면(`versions/page.tsx`)에 있는 "버전 비교" 바로 아래, 또는 산출물 화면의 이슈 목록
위에 새로운 섹션으로 추가하는 걸 제안합니다. Git 이력처럼 왼쪽에 세로 타임라인을 두고, 각
이슈가 버전이 바뀔 때마다 어떻게 됐는지(추가/변경/삭제 없음)를 라벨로 보여주는 구조입니다.

## 구현 순서

1. (백엔드, 선행) `dev_issues`에 버전 연결 컬럼 추가 + 재확정 시 삭제 대신 버전별로 쌓기.
2. 버전 간 이슈 목록 비교 로직(같은 `issueKey`가 있으면 "유지"/제목이 다르면 "변경", 새
   `issueKey`면 "추가", 이전엔 있었는데 이번엔 없으면 "삭제") — 요구사항 본문 diff에 이미 쓰는
   `compareVersions`/`DiffHighlight`와 비슷한 패턴이라 그 경험을 재사용할 수 있습니다.
3. 프론트: 위 와이어프레임대로 타임라인 컴포넌트 하나 추가(`versions/page.tsx`에 섹션으로
   넣거나, 별도 탭으로 분리해도 됨).

이번 UI 리팩토링(디자인 토큰·목록·탭)과는 별도로, 백엔드 스키마 변경이 필요한 기능이라 다음
작업 단위로 분리해서 진행하는 걸 권장합니다.
