# 요구사항 등록 시 질문과 프로젝트 용어사전 자동 정리

## 사용 흐름

1. 요구사항을 등록하면 원문 저장 후 비동기 AI 검토를 시작한다. 같은 프로젝트의 다른 요구사항과 프로젝트 용어사전을 전달한다. 등록 직후 검토 화면에서 기다리면 질문과 새 용어 알림이 나타난다.
2. AI는 모호한 부분을 자연어 질문으로 묻는다. 선택지를 누르거나 직접 답변하고 **답변 반영**을 누르면 질문 대상 문장만 고친다. 수정한 부분은 파란색으로 표시하고 전체 본문을 자동으로 늘려 보여준다. 답변 후 전체 문맥과 기존 요구사항을 다시 검토해 질문을 갱신한다.
3. 모르는 내용은 **나중에 결정**으로 남긴다. 메모와 질문은 서버에 저장되어 새로고침·재접속 후에도 유지한다. **추후 결정** 탭에서 나중에 답변할 수 있다. 보류 자체는 본문에 임의의 조건을 추가하지 않는다.
4. **용어 확인하기** 또는 프로젝트 메뉴 **용어사전**을 연다. AI가 추정한 이름·내용·사용된 요구사항 ID와 원문을 확인한다. 내용을 수정하고 **이 정의로 확정**하거나, 미확정으로 저장하거나, 사용하지 않는 용어로 남긴다.
5. 용어를 수정하면 이전 검토 화면에 재검토 안내가 나타난다. **AI 재검토**를 눌러 새 정의를 반영한다. 남아 있는 질문에 답하거나 추후 결정으로 남긴 뒤 고객 합의·확정을 진행한다.

기존 요구사항도 검토·수정 화면에서 AI 재검토를 실행하면 새 질문과 용어사전 흐름을 사용할 수 있다. 이전에 저장한 원문·버전·합의 이력은 보존한다. 원문과 수정안을 비교하는 화면은 **원문·수정안 비교해서 직접 편집하기** 안에 있다.

## 질문과 검출 범위

| 분류 | 질문 예시 | 처리 원칙 |
|---|---|---|
| 동작 조건 불명확 | 이 동작은 어떤 상황이나 조건에서 발생하나요? | 발생 시점·조건·복합 조건의 적용 관계를 구체화 |
| 수치·판단 기준 불명확 | 응답을 최대 얼마 동안 기다린 뒤 재시도하나요? | 시간·주기·수치·거리 계산·가용 기준을 묻되 값을 임의로 채우지 않음 |
| 수행 주체 불명확 | 이 동작은 누가 수행하나요? | 시스템·운영자 등의 후보는 선택 가능한 예시 |
| 예외 처리 누락 | 설명된 예외 상황이 발생하면 어떻게 처리해야 하나요? | 실패·재시도·알림 등의 후보를 사용자 결정으로 구분 |
| 기존 요구사항과 상충 | 기존 요구사항과 다른 이 기준은 어떤 방향으로 적용해야 하나요? | 실제 기존 요구사항 ID와 원문 근거가 있는 충돌만 필수 확인 |

참조 요구사항 존재 여부는 검출하지 않는다. 시간·일정 모호성은 수치·판단 기준으로 통합했다. 제목이나 단순 나열의 “및”은 그 단어만으로 검출하지 않는다. 예를 들어 “2. 스텝 전환 조건 및 예외 처리”는 질문 대상이 아니다.

질문은 현재 원문을 함께 보여주며 선택지와 자유 입력을 모두 제공한다. 선택지는 확정된 정책이 아니다. 확정된 용어사전에 상태 목록이 있으면 해당 상태를 조건 질문의 후보로 활용한다. 미확정 추정에서 상태나 기준을 사실로 가져오지 않는다.

예: “필요 시 작업을 재할당한다.” → “어떤 상황에서 발생하나요?” → “AMR 통신 장애가 발생했을 때” → “AMR 통신 장애가 발생했을 때 작업을 재할당한다.”

## 용어사전 저장과 확인

| 항목 | 내용 |
|---|---|
| 용어 이름 | 본문에 실제 등장하는 이름. 프로젝트 안에서 이름을 정규화해 중복 방지 |
| 내용 | 문맥을 바탕으로 추정한 의미·적용 범위. AI 최초 추정은 별도로 보존 |
| 어디에 쓰이는지 | 요구사항 내부 ID·표시 ID·실제 사용 구절. 클릭하면 해당 요구사항 검토 화면으로 이동 |
| 확인 상태 | PENDING: 확인 필요 / CONFIRMED: 사용자 확정 / DISMISSED: 사용하지 않음 |
| 수정 충돌 방지 | 버전 번호로 다른 사용자의 변경을 확인하고 오래된 저장을 거절 |

프로젝트 이름·설명과 요구사항의 업무 도메인에 해당하는 핵심 용어만 자동으로 PENDING 등록한다. 일반 단어·일반 IT 약어·개별 상태·구현 심벌은 제외한다. 한국어 용어도 LLM 추출 대상이다. 새로운 용어 등록 시 검토 화면에 알리고, 프로젝트 메뉴에 확인 필요 개수를 표시한다. 알림은 용어사전의 미확인 상태를 기준으로 하며 외부 이메일·푸시는 보내지 않는다.

예: **Task Step** / **VCS에서 태스크를 수행하는 단계. ASSIGNED, MOVE_TO_LOAD 등의 상태를 갖는다.** / **REQ-11 → 해당 요구사항**. AI가 추정한 목록과 의미가 다르면 사용자가 수정한 뒤 확정한다.

후속 등록·재검토는 기존 용어를 재등록하거나 사용자 확정 정의를 덮어쓰지 않는다. 기존 용어가 새로운 요구사항에서 쓰이면 참조를 추가한다. 사용하지 않기로 결정한 용어도 재등록하지 않으며 해당 추정 정의를 분석 근거로 사용하지 않는다. 사용 구절은 각 요구사항의 마지막 검토 본문을 기준으로 갱신한다.

## 분석에 반영하는 방식

- 같은 프로젝트의 다른 요구사항 전문과 용어사전을 AI에 전달한다. 기존 요구사항 비교는 원래의 검토 범위를 유지한다.
- CONFIRMED 정의를 우선 참고한다. PENDING은 추정임을 명시하고, 확정된 업무 규칙처럼 단정하지 않도록 지시한다.
- 규칙 검출도 확정 정의를 참고한다. 예를 들어 확정된 “가용 AMR” 정의가 있으면 이미 정의된 기준을 다시 묻지 않는다. 다른 용어의 상태 목록이나 SOC 범위만으로 가용 기준·SOC 최솟값을 만들어내지는 않는다.
- AI가 현재 본문에 없는 용어·인용을 반환하면 저장하지 않는다. 새 용어 추출의 완료/규칙 대체/실패 상태를 검토 결과와 구분한다.
- 본문·질문 버전과 용어사전 스냅샷을 확인한다. 다른 창에서 변경되었거나 분석 도중 정의가 바뀌면 오래된 답변이나 결과로 덮어쓰지 않는다.
- 답변을 반영할 때 선택된 원문의 정확한 구간만 교체한다. 답변하지 않은 수치·빈칸이 생성되면 거절하고 입력을 유지한다. 최종 의미는 사용자가 본문에서 확인하고 직접 수정할 수 있다.

## 확정 조건

답변할 질문(OPEN)이 있으면 답변하거나 명시적으로 추후 결정(DEFERRED)으로 남겨야 한다. 일반적인 보류 질문은 최종 확정을 막지 않고 계속 보존한다. 실제 기존 요구사항과의 필수 상충 항목은 보류만으로 해결되지 않으며 고객 합의 시 수용 근거를 기록해야 한다. 본문 미입력 표시, 실패·부분 검토, 본문·기존 요구사항·용어사전 변경에 따른 오래된 검토도 서버에서 확인한다.

용어 확인은 본문 확정과 별개다. 미확정 용어가 있다는 이유만으로 확정을 막지는 않으며, 분석에는 불확실한 추정으로 전달한다.

## 적용 방법

1. V007까지 적용된 기존 Oracle DB에서 `db/init.sql` **또는** `db/migrations/V008__clarification_and_glossary.sql`을 한 번 실행한다. 두 파일은 같은 내용이다. 기존 테이블을 삭제하지 않는다.
2. 새 테이블은 `PROJECT_TERMS`, `PROJECT_TERM_USAGES`, `REQUIREMENT_REFINEMENTS`, `CLARIFICATION_QUESTIONS` 네 개다. 이전 검토 기능의 V007이 없으면 먼저 적용한다.
3. AI 서버·백엔드·프론트를 모두 다시 시작한다. npm을 사용할 수 없는 환경은 함께 제공하는 `frontend/dist/standalone`을 사용한다. 새 라이브러리 설치는 필요 없다.
4. 사내 LLM 설정은 기존 `.env`를 유지한다. 이 기능을 위해 새 키나 주소를 추가하지 않는다.

LLM을 사용할 수 없으면 명확하게 도메인을 식별할 수 있는 핵심 용어만 보수적인 규칙으로 추출하고 정확한 의미 확인을 요청한다. 규칙으로 처리 가능한 조건·시간·단일 입력 제안은 답변을 반영할 수 있다. 복잡한 자유 답변은 AI 연결이 필요하며 실패하면 입력을 유지하고 재시도 또는 직접 편집하도록 안내한다. RULE_ONLY는 AI 문맥 검토 완료와 구분해서 표시한다.

## 검증

Python AI 테스트 68건, Java 서비스·HTTP 계약 테스트 67건, 프론트 타입 검사·단위 테스트 14건과 프로덕션 빌드가 통과했다. 브라우저에서는 백엔드 응답을 모사하고 실제 규칙 AI API를 연결해 질문 답변·보류 유지·용어 수정 확정·참조 이동·정의 변경 후 재검토·모바일 레이아웃을 확인한다. Oracle 실제 인스턴스와 사내 LLM의 실제 응답은 이 환경에서 검증하지 못했다.

## AI 처리 중 표시와 확정 버튼

등록 직후 검토, AI 재검토, 답변 반영·질문 갱신 중에는 회전 표시와 경과 시간을 보여준다. 오래 걸리면 AI 응답 대기 중임을 알리고, 완료 시 자동으로 결과를 표시한다. 이 동안 이전 결과의 변경 안내·실패 안내를 표시하지 않는다. 사용자가 수정한 뒤 아직 재검토를 요청하지 않은 상태는 파란색 안내로 구분한다. 요청 진행률을 알 수 없으므로 임의의 퍼센트는 표시하지 않는다.

**‘요구사항 확정’ 버튼**은 처리 중인 요청이 없고, 본문이 비어 있지 않고, 현재 본문·용어사전으로 검토가 저장되어 있으며, 실패/부분 검토가 아니고, OPEN 질문과 미입력 표시가 없어야 활성화된다. RULE_ONLY도 허용하되 AI 문맥 검토 미완료 안내는 유지한다. DEFERRED 질문과 PENDING 용어는 자체적으로 버튼을 막지 않는다. 버튼 옆과 툴팁에 현재 비활성 이유를 표시한다.

**모달의 최종 확정**은 고객 담당자·합의일·합의 내용·변경 요약을 입력해야 한다. 실제 상충 항목에는 고객 결정 근거도 필요하다. 서버는 기존 요구사항이 마지막 검토 후 달라지지 않았는지, 합의 당시 본문이 같은지, 해당 합의를 이미 사용하지 않았는지도 확인한다.

## 422 등 AI 오류 구분

422 상태 숫자만으로 원인을 특정할 수 없다. 기존 `/clarify-answer`는 AI 연결·잘못된 AI 출력 등 모든 예외를 422로 반환했지만 다음처럼 구분한다.

| 상태/코드 | 의미와 화면 안내 |
|---|---|
| 422 / REQUEST_VALIDATION | 필수 필드 누락·잘못된 타입. AI 로그에 요청 경로·필드·오류 종류, 화면에는 확인할 필드와 서버 버전 확인 안내 |
| 422 / ANSWER_NOT_APPLIED | 빈 답변 또는 규칙만으로 처리할 수 없는 자유 답변. 입력을 보존하고 재시도·직접 편집 안내 |
| 502 / ANSWER_GENERATION | 잘못된 JSON·근거 없는 수치·빈칸·변경 없는 AI 문장. 사용자의 입력 오류와 구분 |
| 502 / PROVIDER_HTTP_* 또는 PROVIDER_INVALID_RESPONSE | 사내 AI의 4xx 요청 거절 또는 응답 형식 오류. 실제 upstreamStatus와 확인할 요청 필드 표시 |
| 503 / PROVIDER_* | 실제 모델 서버 사용 불가·연결 실패·요청 제한. 사내 AI 상태와 발생 단계를 구분 |
| 504 / PROVIDER_TIMEOUT | 사내 AI 응답 시간 초과. 모델 목록 조회인지 문장 작성인지 표시 |
| 500 / ANSWER_INTERNAL | 예상하지 못한 서버 처리 오류. 일반 오류 메시지와 진단 코드 기록 |

사용자 환경에서 발생한 특정 422의 요청 경로와 응답 detail은 아직 전달받지 못했으므로 그 실제 원인은 확정하지 않았다. 포트 설정과 사내 AI 주소·키는 변경하지 않는다. 이번 로딩·오류 표시 변경에는 추가 SQL이나 의존성이 필요 없다. 백엔드·AI·프론트를 같은 버전으로 갱신하고 재시작한다.


## 핵심 도메인 용어 선별 기준

프로젝트 이름·설명을 `/analyze.projectContext`로 전달한다. AI는 일반 단어를 모으지 않고, 해당 개념의 프로젝트 고유 의미를 모르면 요구사항을 잘못 해석할 가능성이 큰 경우만 선정한다. HIGH 중요도·업무 개념 분류·도메인 선정 이유를 요구하고 검증한다. 한국어 용어도 같은 기준으로 처리한다. 보통 0~3개, 새 후보는 요구사항당 최대 5개이며 개수를 채우지 않는다.

- VCS 프로젝트 후보 예: VCS, AMR, SOC, Task Step. 다른 프로젝트에 VCS 용어를 강제로 넣지 않는다.
- 제외 예: 시스템, 사용자, 화면, 상태, API, JSON, UI, ID, 요구사항 ID, DTO·Controller 같은 구현 이름.
- ASSIGNED·MOVE_TO_LOAD 같은 개별 상태는 Task Step 등 상위 개념의 정의에 설명한다.
- VCS와 Vehicle Control System 같은 약어·풀네임은 중복 등록하지 않는다.
- AI 미연결 시 대문자·영어 이름이라는 이유만으로 전부 추출하던 규칙을 제거했다. 판단할 수 없는 용어는 등록하지 않는다.

새 기준은 이후 등록·재검토에서 생성하는 후보에 적용한다. 이미 저장된 정의·확인 이력은 자동 삭제하지 않는다. 기존 불필요 항목은 용어사전에서 ‘사용하지 않음’으로 처리할 수 있다.

## 사내 AI 실제 호출과 503 원인 구분

요구사항 검토와 답변 반영은 동일한 provider 인스턴스를 사용한다. 사내 LLM에는 동일한 `POST {LLM_API_BASE}/chat/completions`로 model/messages(system,user)/temperature를 보낸다. 답변 반영은 질문·답변·선택 문장·용어사전을 포함하는 문장 작성 프롬프트가 다르다. 주소·키·모델 설정은 변경하지 않는다.

`model=auto`이면 처음 성공한 `/models` 결과를 현재 프로세스에서 재사용한다. 매번 모델 목록을 새로 요청하지 않는다. 최초 모델 조회 실패와 문장 생성 요청 실패를 stage로 구분한다.

이전 코드는 모든 ProviderError를 503으로 변환했으므로 사용자가 본 503이 실제 사내 서버의 503이라는 뜻은 아니었다. 사내 HTTP 400·401·422 거절은 로컬 502와 실제 upstreamStatus로, 시간 초과는 504로, 실제 연결 실패·사내 5xx·429 제한은 503으로 구분한다. 서버가 반환한 안전한 요청 필드명(param)이 있으면 표시하고, 사내 주소·인증값·오류 원문은 노출하지 않는다.

사내 AI 실패 시 기존 검토는 규칙 결과를 유지하면서 PARTIAL로 표시하지만 자유 답변의 문장 작성은 실패한다. 이를 문장 작성 성공으로 처리하거나 원문을 임의로 바꾸지 않는다. 이 환경에서는 사내 서버에 접근할 수 없으므로 특정 사용자가 겪은 호출 실패의 실제 원인은 응답 코드/단계 확인이 필요하다.

로컬 HTTP 모델 서버를 이용해 정상 검토·답변의 동일한 전송 규격, 모델 조회 재사용, 사내 HTTP 400/401/422/429/503, 모델 조회 403, 잘못된 모델 응답을 검증했다. 추가 SQL·의존성 설치·프론트 빌드 변경 없이 AI와 백엔드를 갱신·재시작한다.
