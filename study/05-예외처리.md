# 예외 처리 — 예외를 HTTP 상태코드로 바꾸는 구조

## 왜 이렇게 나눴나

`ApiErrors.java`와 `GlobalExceptionHandler.java`는 역할이 완전히 분리돼 있다.

```java
// ApiErrors.java — "무슨 일이 있었는지"만 표현
public final class ApiErrors {
    public static class ProjectNotFound extends RuntimeException {
        public ProjectNotFound(Long id) {
            super("프로젝트를 찾을 수 없습니다: " + id);
        }
    }
    public static class NotProjectOwner extends RuntimeException { ... }
    public static class NotProjectMember extends RuntimeException { ... }
    public static class InvalidProjectToken extends RuntimeException { ... }
    public static class DuplicateEmpNo extends RuntimeException { ... }
    public static class InvalidLogin extends RuntimeException { ... }
}
```

```java
// GlobalExceptionHandler.java — "그 일이 HTTP로 몇 번인지"만 표현
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(ApiErrors.ProjectNotFound.class)
    public ResponseEntity<Map<String, String>> handleProjectNotFound(ApiErrors.ProjectNotFound e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(Map.of("message", e.getMessage()));
    }
    ...
}
```

`ProjectService`는 `throw new ApiErrors.ProjectNotFound(projectId);`라고만 쓸 뿐, **HTTP를 전혀 모른다.** "404" 같은 개념 자체가 서비스 계층 코드 어디에도 없다. HTTP는 웹으로 노출할 때만 의미가 있는 개념이지, 비즈니스 로직 입장에선 몰라야 정상이다(같은 서비스 로직을 나중에 gRPC나 배치 작업에서 재사용해도 문제가 없어야 하니까). "예외 → 상태코드" 변환 책임은 `GlobalExceptionHandler` 한 곳에만 몰아둬서, 나중에 "이 에러는 404 대신 409로 바꾸자"는 결정이 나도 서비스 코드는 하나도 안 건드리고 여기만 고치면 된다.

## `@RestControllerAdvice` + `@ExceptionHandler`가 실제로 하는 일

`DispatcherServlet`은 요청 처리 과정에서 예외가 던져지고 아무도 잡지 않으면, 등록된 `@ExceptionHandler` 메서드 중에 **그 예외 타입과 일치하거나 그 예외의 부모 타입을 처리하는 걸 선언한 메서드**가 있는지 찾는다. `@RestControllerAdvice`가 붙은 클래스 안의 `@ExceptionHandler`는 **애플리케이션 전역의 모든 `@RestController`**에 적용된다(클래스 하나하나에 예외 처리를 반복해서 안 써도 됨).

이 프로젝트의 매핑:

| 예외 | HTTP 상태 | 상황 |
|---|---|---|
| `ApiErrors.DuplicateEmpNo` | 409 Conflict | 회원가입 시 사번 중복 |
| `ApiErrors.InvalidLogin` | 401 Unauthorized | 로그인 실패 |
| `ApiErrors.ProjectNotFound` | 404 Not Found | 없는 프로젝트 id 조회 |
| `ApiErrors.NotProjectOwner` / `NotProjectMember` | 403 Forbidden | 권한 없음 |
| `ApiErrors.InvalidProjectToken` | 400 Bad Request | 참여 토큰이 잘못되었거나 폐기됨 |

```java
@ExceptionHandler({ApiErrors.NotProjectOwner.class, ApiErrors.NotProjectMember.class})
public ResponseEntity<Map<String, String>> handleForbidden(RuntimeException e) {
    return ResponseEntity.status(HttpStatus.FORBIDDEN).body(Map.of("message", e.getMessage()));
}
```

한 메서드가 여러 예외 타입을 동시에 처리할 수도 있다 — `NotProjectOwner`든 `NotProjectMember`든 결과는 똑같이 403이니 배열로 묶었다.

## 우리가 안 잡은 예외는 어떻게 되나

`GlobalExceptionHandler`에 없는 예외(예: DB 연결 실패로 인한 `DataAccessException`, 테이블이 없어서 나는 `SQLException` 계열)가 터지면, 스프링 부트가 기본 제공하는 `BasicErrorController`가 대신 처리한다. 이때 나가는 응답은:

```json
{ "timestamp": "...", "status": 500, "error": "Internal Server Error", "path": "/api/projects" }
```

기본 설정(`server.error.include-message=never`)에서는 `message` 필드가 아예 빠진다(보안상 내부 에러 메시지를 클라이언트에 노출하지 않기 위해). 그래서 프론트의 `app/lib/api.ts`가 이런 응답을 받으면 `data?.message`가 없어서 "요청이 실패했습니다"라는 기본 문구를 보여주게 된다 — 이게 폐쇄망 DB 미설정 때 봤던 그 메시지의 정체다.

## `@Valid` 실패는 어디서 처리되는가

`MethodArgumentNotValidException`(검증 실패)은 `ApiErrors`에 없는데도 400이 나간다. 이건 스프링 웹이 **기본으로 이미 처리해주는** 예외라서 그렇다 — `ResponseEntityExceptionHandler`(스프링이 내부적으로 갖고 있는 핸들러)가 이 타입을 알아서 400으로 바꿔준다. 우리가 `GlobalExceptionHandler`에 직접 추가한 건 **우리가 정의한 도메인 예외들**뿐이고, 스프링/Bean Validation이 이미 처리해주는 것까지 중복으로 짤 필요는 없다.

## 흐름 요약 (다시)

```
서비스 코드: throw new ApiErrors.XXX(...)
        ↓ (아무도 안 잡음, 계속 위로 전파)
컨트롤러: 그냥 통과
        ↓
DispatcherServlet: "이 예외 타입 처리하는 @ExceptionHandler 있나?" 탐색
        ↓ 있음
GlobalExceptionHandler.handleXXX(e) 실행
        ↓
ResponseEntity(상태코드 + {"message": "..."}) 반환 → 클라이언트로 응답
```
