# 계층형 아키텍처 — 패키지를 이렇게 나눈 이유

## 전체 구조

```
com.semes.reqops
├── ReqopsApplication.java
├── global/                     ← "비즈니스 의미가 없는" 코드
│   ├── config/                 CorsConfig
│   └── exception/               ApiErrors, GlobalExceptionHandler
└── domain/                     ← 실제 비즈니스 로직이 있는 코드
    ├── user/
    │   ├── entity/User.java
    │   └── repository/UserRepository.java
    ├── auth/
    │   ├── controller/AuthController.java
    │   ├── dto/AuthDto.java
    │   └── service/AuthService.java
    └── project/
        ├── controller/ProjectController.java
        ├── dto/ProjectDto.java
        ├── entity/{Project,Membership,ProjectToken,Role}.java
        ├── repository/{Project,Membership,ProjectToken}Repository.java
        └── service/ProjectService.java
```

## `global` vs `domain`을 가르는 기준

**`global`은 "이 코드만 보고는 이 서비스가 뭘 하는 앱인지 전혀 알 수 없는" 코드만 들어간다.** CORS 설정이나 예외를 HTTP 상태로 바꾸는 로직은 요구사항 관리 시스템이 아니라 어떤 웹 서비스에 갖다 놔도 똑같이 쓸 수 있다 — 순수 인프라.

**`domain`은 "이 코드가 곧 이 앱이 하는 일"인 코드.** `ProjectService`를 읽으면 "아, 이 앱은 프로젝트를 만들고 토큰으로 초대하는 기능이 있구나"를 알 수 있다.

이 프로젝트 초반에는 `auth`를 `global`에 넣을지 고민한 적이 있다 — "인증"이 왠지 인프라스러워 보여서. 하지만 실제로 `AuthService`가 하는 일(사번 중복 검사, 비밀번호 대조)은 **User라는 도메인 데이터를 다루는 비즈니스 로직**이지, JWT 필터나 시큐리티 설정 같은 순수 인프라가 아니다. 그래서 `domain/auth`로 갔다. (반대로 나중에 JWT 발급/검증 필터를 추가한다면, 그 필터 자체는 `global`에 들어가는 게 맞다 — 그건 "인증이 필요한 모든 요청에 공통으로 걸리는 인프라"니까.)

## `domain` 안에서 도메인별로 나눈 이유 (패키지 바이 피처)

`domain/user`, `domain/auth`, `domain/project`처럼 **기능 단위로 패키지를 나누고**, 그 안에 레이어(controller/service/repository/entity/dto)를 다시 나누는 방식이다. 대안은 최상위에 `controller/`, `service/`, `repository/`를 두고 그 안에 모든 도메인 클래스를 섞어 넣는 "레이어 우선" 방식인데, 그건:

- 파일 수가 적을 땐 상관없지만 늘어나면 `controller/` 폴더 하나에 관련 없는 클래스 수십 개가 뒤섞임
- "프로젝트 관련 코드를 전부 지우고 싶다"처럼 기능 단위 작업을 할 때 여러 폴더를 오가야 함

패키지 바이 피처는 반대로 "프로젝트 기능"이 폴더 하나(`domain/project`)에 다 모여있어서 응집도가 높다.

## 각 레이어의 역할과 의존 방향

```
controller → service → repository → entity
    ↓            ↓
   dto      (dto ↔ entity 변환은 항상 service가 함)
```

- **controller**: HTTP 요청/응답만 다룸. 비즈니스 로직 없음. `ProjectController`의 모든 메서드가 한 줄짜리 위임인 것 참고.
- **service**: 실제 로직. 트랜잭션 경계(`@Transactional`)가 여기 있음. 엔티티를 조작하고, DTO로 변환해서 컨트롤러에 돌려줌.
- **repository**: DB 접근만. `JpaRepository` 상속 인터페이스, 메서드 이름이 곧 쿼리.
- **entity**: DB 테이블과 1:1 매핑되는 객체. `getter`는 있어도 무분별한 `setter`는 없고, 상태를 바꾸는 메서드는 의미 있는 이름을 가짐(`Project.update()`, `ProjectToken.revoke()`) — "아무나 아무 필드나 막 바꿀 수 있는" 빈약한 객체가 되지 않도록.
- **dto**: 요청/응답 전용 데이터 형태. 엔티티를 API 응답에 직접 노출하지 않는 이유는 [07-DTO-record.md](07-DTO-record.md) 참고.

## 컨트롤러가 엔티티를 직접 다루지 않는 이유

`ProjectController.create()`는 `Project` 엔티티를 한 번도 안 보고, `CreateRequest`/`DetailResponse` 같은 DTO만 다룬다. 만약 컨트롤러가 엔티티를 직접 리턴한다면:

- 엔티티의 `password`, 내부 구현 세부사항(예: 앞으로 추가될 내부용 필드)까지 그대로 JSON에 노출될 위험
- DB 스키마가 바뀌면 API 응답 형태도 자동으로 같이 바뀌어버림 — DB와 API 계약이 강하게 결합됨
- 엔티티에 지연 로딩 연관관계가 있다면 JSON 직렬화 시점에 예상치 못한 추가 쿼리(N+1)나 순환 참조 직렬화 오류가 날 수 있음

그래서 항상 **서비스 계층이 엔티티 → DTO 변환을 책임지고, 그 경계 밖(컨트롤러, API 응답)으로는 DTO만 나간다.**

## "세션 없이 `userId`를 직접 받는다"는 이례적인 설계

실무 표준이라면 `ProjectController`가 `userId`를 파라미터로 받지 않고, 인증 필터가 토큰을 검증해서 `SecurityContext`에 넣어둔 사용자 정보를 컨트롤러가 꺼내 쓰는 식이다. 이 프로젝트는 세션/JWT를 의도적으로 뺐기 때문에(`기능명세서.md` NFR), 프론트가 로그인 후 받은 `userId`를 **매 요청마다 명시적으로** 실어 보내는 방식으로 단순화했다. 이건 "표준"이 아니라 "학습 목적의 단순화"라는 걸 분명히 알고 넘어가는 게 중요하다 — 실무에서 이렇게 짜면 다른 사용자의 `userId`를 임의로 넣어 API를 호출할 수 있는 심각한 보안 문제가 된다.
