# 요청 처리 흐름 — API 하나가 들어와서 응답이 나가기까지

`POST /api/projects/join` (토큰으로 프로젝트 참여) 요청 하나를 처음부터 끝까지 따라가본다.

```json
POST /api/projects/join
{ "userId": 3, "token": "req_prj_9f3a2c..." }
```

## 0단계 — 요청이 톰캣에 도착

스프링 부트는 내장 톰캣(Tomcat) 서버를 갖고 있다. `mvn spring-boot:run`으로 앱을 띄우면 이 톰캣이 8080 포트에서 HTTP 요청을 기다린다. 요청이 오면 톰캣이 그걸 받아서 서블릿 컨테이너 규격에 맞는 `HttpServletRequest` 객체로 감싼다.

## 1단계 — `DispatcherServlet`이 요청을 받음

스프링 MVC는 `DispatcherServlet`이라는 단 하나의 서블릿이 `/` 이하 모든 요청을 다 받는 구조다(프론트 컨트롤러 패턴). `DispatcherServlet`은 요청을 직접 처리하지 않고, "이 URL과 메서드를 처리할 자바 메서드가 뭔지" 찾는 일부터 시작한다.

## 2단계 — `HandlerMapping`이 컨트롤러 메서드를 찾음

앱이 시작할 때 스프링은 `@RequestMapping` 계열 어노테이션이 붙은 메서드를 전부 스캔해서 "URL 패턴 + HTTP 메서드 → 처리할 자바 메서드" 매핑 테이블을 만들어둔다. 이 요청은:

```java
// ProjectController.java
@PostMapping("/join")
public SummaryResponse join(@Valid @RequestBody JoinRequest request) {
    return projectService.join(request);
}
```

클래스 레벨 `@RequestMapping("/api/projects")` + 메서드 레벨 `@PostMapping("/join")` = `POST /api/projects/join`. `HandlerMapping`이 이 매핑을 찾아서 `DispatcherServlet`에게 "이 메서드로 가면 된다"고 알려준다.

## 3단계 — 파라미터 바인딩 (`HandlerMethodArgumentResolver`)

`join(@Valid @RequestBody JoinRequest request)`의 파라미터를 실제로 채우는 단계.

1. `@RequestBody`를 보고 `RequestResponseBodyMethodProcessor`(리졸버)가 나섬
2. `Content-Type: application/json` 헤더를 보고 Jackson의 `ObjectMapper`를 사용하기로 결정
3. 요청 바디 JSON `{"userId": 3, "token": "req_prj_..."}`을 읽어서, `JoinRequest`의 정규 생성자(record라 하나뿐)를 리플렉션으로 찾음
4. JSON 필드명(`userId`, `token`)과 record 컴포넌트명을 매칭시켜 `new JoinRequest(3L, "req_prj_...")` 실행

```java
// ProjectDto.java
public record JoinRequest(
        @NotNull Long userId,
        @NotBlank String token
) {}
```

## 4단계 — 검증 (`@Valid`)

`JoinRequest` 객체가 만들어지자마자, `@Valid`가 붙어 있으므로 Bean Validation이 개입한다. `userId`가 `null`인지(`@NotNull`), `token`이 빈 문자열인지(`@NotBlank`) 검사. 하나라도 위반하면 `MethodArgumentNotValidException`을 던지고, 컨트롤러 메서드 본문은 **아예 실행되지 않은 채** 스프링이 기본 제공하는 핸들러가 400 응답을 만들어 여기서 흐름이 끝난다.

통과하면 5단계로.

## 5단계 — 컨트롤러 메서드 실행

```java
public SummaryResponse join(@Valid @RequestBody JoinRequest request) {
    return projectService.join(request);
}
```

컨트롤러는 딱 한 줄, `projectService.join(request)`만 호출하고 서비스가 리턴한 값을 그대로 돌려준다. **비즈니스 로직을 전혀 안 갖고 있다** — 이게 컨트롤러의 역할: 요청을 받아 서비스에 넘기고, 서비스 결과를 응답 형태로 내보내는 것뿐. 실제 로직은 다음 단계.

## 6단계 — 서비스 계층, 트랜잭션 시작

```java
// ProjectService.java
@Transactional
public SummaryResponse join(JoinRequest req) {
    ProjectToken token = projectTokenRepository.findByTokenAndRevokedFalse(req.token())
            .orElseThrow(ApiErrors.InvalidProjectToken::new);
    Long projectId = token.getProjectId();

    if (!membershipRepository.existsByUserIdAndProjectId(req.userId(), projectId)) {
        membershipRepository.save(new Membership(req.userId(), projectId, Role.MEMBER));
    }

    Project project = projectRepository.findById(projectId)
            .orElseThrow(() -> new ApiErrors.ProjectNotFound(projectId));
    int memberCount = membershipRepository.findByProjectId(projectId).size();
    return new SummaryResponse(project.getId(), project.getName(), project.getCustomer(),
            project.getDescription(), Role.MEMBER.name(), memberCount);
}
```

`@Transactional`이 붙은 메서드를 호출하는 순간, 사실은 `projectService` 빈이 진짜 `ProjectService` 객체가 아니라 **스프링이 만든 프록시 객체**라는 게 중요해진다(자세한 건 [03-영속성-JPA.md](03-영속성-JPA.md)와 아래 "프록시" 절 참고). 프록시가 다음을 대신 해준다:

1. 실제 `join()` 코드를 실행하기 **전에** DB 커넥션을 얻고 트랜잭션 시작(`BEGIN`)
2. 진짜 `join()` 메서드 실행 — 여기서부터가 우리가 짠 코드
3. 정상 종료되면 커밋, 예외가 터지면 롤백

## 7단계 — 리포지토리 → JPA/Hibernate → JDBC → DB

`projectTokenRepository.findByTokenAndRevokedFalse(...)`를 호출하면:

1. Spring Data JPA가 메서드 이름을 분석해 만들어둔 JPQL 실행: `SELECT t FROM ProjectToken t WHERE t.token = :token AND t.revoked = false`
2. Hibernate가 이 JPQL을 실제 SQL로 변환: `SELECT * FROM project_tokens WHERE token = ? AND revoked = 0`
3. JDBC 드라이버(`ojdbc11`)가 이 SQL을 Oracle에 실제로 전송
4. 결과 행(row)을 다시 `ProjectToken` 객체로 매핑(이 시점에 이 객체는 **영속 상태**가 됨 — 현재 트랜잭션의 영속성 컨텍스트에 등록)

토큰이 없거나 `revoked=1`이면 `Optional`이 비어서 `orElseThrow(ApiErrors.InvalidProjectToken::new)`가 실행되고, 여기서 예외가 던져지면서 서비스 메서드는 즉시 종료된다(트랜잭션은 롤백되지만, 지금까진 아무 것도 안 바꿨으니 롤백할 것도 없음).

토큰이 유효하면, `membershipRepository.existsByUserIdAndProjectId(...)`로 이미 멤버인지 확인하고 아니면 `save(new Membership(...))`로 새 멤버십을 INSERT(비영속 객체라 `persist`). 그다음 프로젝트 정보를 조회해서 응답용 `SummaryResponse`를 만들어 리턴한다.

## 8단계 — 메서드 정상 종료, 트랜잭션 커밋

`join()`이 예외 없이 리턴하면, 프록시가 flush(변경사항을 실제 SQL로 내보냄) + `COMMIT`을 실행한다. 이 시점에 방금 INSERT한 멤버십이 실제로 DB에 영구 반영된다.

## 9단계 — 응답 직렬화, 역순으로 되돌아감

`join()`이 리턴한 `SummaryResponse` 객체가 컨트롤러까지 그대로 리턴되고, `@RestController`(= `@ResponseBody`)이므로 Jackson이 이 객체를 JSON 문자열로 직렬화한다:

```json
{ "id": 1, "name": "VCS · 태스크 할당", "customer": "삼성전자 EDS", "description": "...", "role": "MEMBER", "memberCount": 4 }
```

`@ResponseStatus`가 없으니 기본값 `200 OK`로 응답 상태코드가 설정되고, `DispatcherServlet` → 톰캣 → 클라이언트(Next.js `fetch`) 순으로 응답이 내려간다.

## 예외가 나면 어떻게 우회되는가

만약 토큰이 잘못돼서 `ApiErrors.InvalidProjectToken`이 던져졌다면, 6~8단계의 정상 흐름 대신:

1. `@Transactional` 프록시가 예외를 감지 → 롤백
2. 예외가 서비스 → 컨트롤러 → `DispatcherServlet`까지 계속 위로 던져짐(아무도 `catch` 안 했으므로)
3. `DispatcherServlet`이 이 예외 타입을 처리할 수 있는 `@ExceptionHandler`를 찾음 → `GlobalExceptionHandler.handleInvalidToken()` 발견
4. 그 메서드가 리턴한 `ResponseEntity`(상태코드 400 + 메시지 JSON)가 응답으로 나감

자세한 건 [05-예외처리.md](05-예외처리.md).

## "프록시로 동작한다"는 게 정확히 뭔 소리인가

`@Transactional`, `@Async` 같은 어노테이션은 **AOP(관점 지향 프로그래밍)**로 구현된다. 컨테이너가 `ProjectService` 빈을 등록할 때, `@Transactional`이 붙은 메서드가 하나라도 있으면 진짜 `ProjectService` 대신 **그걸 감싸는 프록시 객체**를 만들어서 빈으로 등록한다. `ProjectController`가 주입받는 `projectService`는 사실 이 프록시다. 그래서:

```java
projectService.join(request);
```

는 실제로는:

```java
proxy.join(request);
// proxy 내부: 트랜잭션 시작 → 진짜 target.join(request) 호출 → 커밋/롤백
```

이렇게 동작한다. (참고: 같은 클래스 안에서 `this.join()`처럼 자기 자신의 메서드를 직접 호출하면 프록시를 거치지 않아서 `@Transactional`이 무시된다는 유명한 함정이 있는데, 이 프로젝트 서비스들은 그런 자기 호출이 없어서 해당 사항 없음.)
