# 어노테이션 — 이 프로젝트에서 쓰는 것 전부

어노테이션은 그 자체로는 아무 동작도 안 한다. **누군가(스프링 컨테이너, Hibernate, 검증기)가 리플렉션으로 그 어노테이션이 붙어있는지 읽어서 행동을 바꾸는 것**뿐이다. 이 문서는 "이 어노테이션을 읽는 게 누구고, 뭘 하는지"를 기준으로 정리했다.

---

## 1. 빈 등록 — 스프링이 객체를 만들게 하는 어노테이션

### `@SpringBootApplication`
`ReqopsApplication.java`에 딱 하나 있다.

```java
@SpringBootApplication
public class ReqopsApplication {
    public static void main(String[] args) {
        SpringApplication.run(ReqopsApplication.class, args);
    }
}
```

내부적으로 `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan` 3개를 합쳐놓은 어노테이션이다. 실질적으로 중요한 건 `@ComponentScan`인데, 이 클래스가 있는 패키지(`com.semes.reqops`)부터 **하위 패키지 전부를 훑으면서** `@Component` 계열 어노테이션이 붙은 클래스를 전부 찾아 빈으로 등록한다. 그래서 `domain.project.service.ProjectService`처럼 깊이 들어가 있어도 자동으로 스캔된다 — 패키지가 `ReqopsApplication`보다 아래에 있기만 하면 된다.

### `@RestController`
`AuthController`, `ProjectController`에 붙어있다.

```java
@RestController
@RequestMapping("/api")
public class AuthController { ... }
```

`@Controller` + `@ResponseBody`를 합친 것. `@Controller`만 있으면 메서드 리턴값을 "뷰 이름"으로 해석해서 HTML 템플릿을 찾으려 하는데(옛날 JSP/Thymeleaf 방식), `@ResponseBody`가 있으면 리턴값을 **그대로 JSON으로 직렬화해서 응답 바디에 씀**. REST API를 만들 땐 무조건 `@RestController`를 쓴다고 보면 된다.

### `@Service`
`AuthService`, `ProjectService`에 붙어있다. 기능적으로는 `@Component`와 완전히 동일 — 빈 등록만 놓고 보면 차이가 없다. 그런데도 굳이 `@Service`를 쓰는 이유는 **"이건 비즈니스 로직을 담당하는 계층"이라는 의미를 코드에 남기기 위해서**다(사람이 읽을 때도, 나중에 AOP로 서비스 계층에만 공통 로직을 걸고 싶을 때도 구분이 필요함).

### `@Configuration` + `@Bean`
`CorsConfig`에서 쓴다.

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) { ... }
}
```

`@Configuration`은 "이 클래스는 빈을 정의하는 설정 클래스"라는 뜻. 이 프로젝트에선 `@Bean` 메서드를 직접 쓰진 않고 `WebMvcConfigurer` 인터페이스를 구현하는 방식(콜백 등록형)을 썼는데, 이것도 결국 `@Configuration` 클래스가 스프링에게 "MVC 설정을 커스터마이징하겠다"고 알리는 방식 중 하나다.

### `@RestControllerAdvice`
`GlobalExceptionHandler`에 붙어있다. `@ControllerAdvice` + `@ResponseBody`의 조합으로, "모든 `@RestController`에서 발생하는 특정 예외를 가로채는 전역 핸들러"를 등록한다. 자세한 동작은 [05-예외처리.md](05-예외처리.md) 참고.

## 2. 의존성 주입

### `@RequiredArgsConstructor` (Lombok)
`AuthController`, `AuthService`, `ProjectController`, `ProjectService`에 다 붙어있다.

```java
@Service
@RequiredArgsConstructor
public class ProjectService {
    private final ProjectRepository projectRepository;
    private final MembershipRepository membershipRepository;
    ...
}
```

이건 스프링 어노테이션이 아니라 **Lombok 어노테이션**이다. 컴파일 타임에 `final` 필드를 전부 파라미터로 받는 생성자를 자동으로 만들어준다. 즉 위 코드는 컴파일되면 사실상 이렇게 된다:

```java
public ProjectService(ProjectRepository projectRepository, MembershipRepository membershipRepository, ...) {
    this.projectRepository = projectRepository;
    this.membershipRepository = membershipRepository;
    ...
}
```

그리고 스프링은 **생성자가 하나뿐인 빈은 `@Autowired` 없이도 자동으로 생성자 주입을 해준다** (스프링 4.3+ 규칙). 그래서 이 프로젝트 어디에도 `@Autowired`가 안 보이는 것 — Lombok이 생성자를 만들고, 스프링이 그 생성자를 보고 알아서 필요한 빈들을 찾아 넣어준다.

**왜 필드 주입(`@Autowired private XXX xxx;`) 대신 생성자 주입을 쓰나?**
- 필드가 `final`이라 한 번 주입되면 재할당 불가 → 불변성 보장
- 테스트 코드에서 `new ProjectService(mockRepo, ...)`처럼 목(mock)을 직접 넣기 쉬움
- 순환 참조(A가 B를 필요로 하고 B가 A를 필요로 하는 상황)가 있으면 앱 시작 시점에 바로 에러가 나서 발견하기 쉬움(필드 주입은 이 문제를 늦게, 런타임에 가서야 들키게 함)

## 3. 요청 매핑 — HTTP 요청을 자바 메서드에 연결

### `@RequestMapping`, `@PostMapping`, `@GetMapping`, `@PatchMapping`
`ProjectController` 예시:

```java
@RestController
@RequestMapping("/api/projects")
public class ProjectController {

    @PostMapping
    public DetailResponse create(...) { ... }      // POST /api/projects

    @GetMapping
    public List<SummaryResponse> list(...) { ... } // GET /api/projects

    @GetMapping("/{id}")
    public DetailResponse detail(...) { ... }       // GET /api/projects/{id}

    @PatchMapping("/{id}")
    public DetailResponse update(...) { ... }        // PATCH /api/projects/{id}
}
```

클래스 레벨의 `@RequestMapping("/api/projects")`가 "기본 경로"를 정하고, 메서드 레벨의 `@PostMapping`/`@GetMapping`등이 **HTTP 메서드 + 나머지 경로**를 합쳐서 최종 라우팅 규칙을 만든다. 스프링은 앱이 뜰 때 이 정보를 전부 모아서 "URL 패턴 → 메서드" 매핑 테이블(`HandlerMapping`)을 만들어두고, 요청이 올 때마다 이 테이블을 찾아본다. 자세한 흐름은 [04-요청처리흐름.md](04-요청처리흐름.md).

### `@RequestBody`
```java
public UserResponse signup(@Valid @RequestBody SignupRequest request)
```
요청의 JSON 바디를 자바 객체로 역직렬화(JSON → `SignupRequest`)한다. 내부적으로 Jackson 라이브러리가 리플렉션으로 `SignupRequest`의 생성자(record는 정규 생성자 하나뿐)를 찾아서 JSON 필드명과 매칭시켜 값을 채운다.

### `@RequestParam`
```java
public List<SummaryResponse> list(@RequestParam Long userId)
```
쿼리스트링(`?userId=1`)에서 값을 꺼낸다. `@RequestParam Long userId`처럼 기본형이 아닌 래퍼 타입(`Long`)이면 필수 파라미터가 되고, 없으면 400 에러가 난다.

### `@PathVariable`
```java
public DetailResponse detail(@PathVariable Long id, @RequestParam Long userId)
```
URL 경로 자체(`/api/projects/{id}`)에서 `{id}` 부분을 꺼내 파라미터에 바인딩한다.

### `@ResponseStatus`
```java
@PostMapping("/signup")
@ResponseStatus(HttpStatus.CREATED)
public UserResponse signup(...) { ... }
```
정상 응답의 HTTP 상태 코드를 지정한다. 이게 없으면 스프링은 기본으로 `200 OK`를 쓴다. 회원가입·프로젝트 생성처럼 "새로 만들어졌다"는 의미를 담을 땐 REST 관례상 `201 Created`를 쓰는 게 맞아서 명시적으로 붙였다.

## 4. 검증(Validation)

### `@Valid`
```java
public UserResponse signup(@Valid @RequestBody SignupRequest request)
```
`@RequestBody`로 객체가 다 만들어진 **직후**, 그 객체 필드에 붙은 검증 어노테이션(`@NotBlank` 등)을 실제로 검사하라는 트리거. `@Valid`가 없으면 `@NotBlank`가 붙어있어도 아무 검사도 안 일어난다.

### `@NotBlank`, `@NotNull`
`AuthDto.java`, `ProjectDto.java`에서 쓴다.

```java
public record SignupRequest(
        @NotBlank String empNo,
        @NotBlank String name,
        String dept,
        @NotBlank String password
) {}
```

```java
public record CreateRequest(
        @NotNull Long userId,
        @NotBlank String name,
        ...
) {}
```

- `@NotBlank`: `String`이 `null`도 아니고, 공백만 있는 것도 아니어야 함(`""`, `"   "` 다 실패)
- `@NotNull`: 그냥 `null`이 아니면 됨. `Long userId`처럼 문자열이 아닌 타입엔 `@NotBlank`를 못 쓰니 `@NotNull`을 쓴다.

검증에 실패하면 `MethodArgumentNotValidException`이 발생하고, 컨트롤러 메서드 본문은 아예 실행되지 않은 채 400 응답이 나간다(이 예외는 스프링이 기본으로 처리해줌 — 우리가 만든 `GlobalExceptionHandler`가 따로 안 잡아도 400이 나가는 이유).

## 5. JPA 엔티티 어노테이션

`User.java`, `Project.java`, `Membership.java`, `ProjectToken.java` 공통.

### `@Entity`, `@Table`
```java
@Entity
@Table(name = "PROJECTS")
public class Project { ... }
```
`@Entity`는 "이 클래스는 JPA가 관리하는 영속 객체"라고 선언하는 것. `@Table(name=...)`로 매핑할 실제 DB 테이블명을 지정한다(안 쓰면 클래스명을 그대로 테이블명으로 씀).

### `@Id`, `@GeneratedValue`
```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```
`@Id`는 기본키(PK) 필드 표시. `@GeneratedValue(strategy = IDENTITY)`는 "값 생성을 DB한테 맡긴다"는 뜻 — Oracle의 `GENERATED BY DEFAULT AS IDENTITY` 컬럼과 짝이 맞는 전략이다(`db/init.sql` 참고). INSERT를 실제로 날려봐야 DB가 id를 채번해서 알려주기 때문에, `IDENTITY` 전략에서는 배치 insert 최적화가 제한된다는 특징이 있다(지금 규모에선 무관).

### `@Column`
```java
@Column(name = "emp_no", nullable = false, unique = true, length = 20)
private String empNo;
```
필드 ↔ 컬럼 매핑 상세 옵션. `name`으로 실제 컬럼명(카멜케이스 `empNo` ↔ 스네이크케이스 `emp_no`)을 지정하고, `nullable`/`unique`/`length`는 **스키마 자동 생성 시에만** 의미가 있다(이 프로젝트는 `ddl-auto: none`이라 `db/init.sql`로 테이블을 직접 관리하므로, 이 옵션들은 사실상 "문서화" 역할에 가깝다 — 실제 제약은 SQL에 있는 게 진짜다).

### `@Enumerated`
`Membership.java`:
```java
@Enumerated(EnumType.STRING)
@Column(nullable = false, length = 20)
private Role role;
```
자바 enum(`Role.OWNER`, `Role.MEMBER`)을 DB에 저장하는 방식을 지정. `EnumType.STRING`이면 문자열 그대로("OWNER") 저장되고, `EnumType.ORDINAL`(기본값)이면 순서 번호(0, 1)로 저장된다. **ORDINAL은 나중에 enum 순서가 바뀌면 기존 데이터가 다 틀어지는 함정**이 있어서 실무에서는 거의 항상 STRING을 쓴다.

### `@PrePersist`
```java
@PrePersist
void onCreate() {
    this.createdAt = LocalDateTime.now();
}
```
JPA 라이프사이클 콜백. "이 엔티티가 처음 DB에 INSERT되기 직전"에 자동 호출된다. `created_at`처럼 "생성 시각은 항상 지금"이어야 하는 필드를 사람이 실수로 빼먹지 않도록 여기서 강제로 채운다.

## 6. 트랜잭션

### `@Transactional`
```java
@Transactional
public DetailResponse create(CreateRequest req) { ... }

@Transactional(readOnly = true)
public List<SummaryResponse> list(Long userId) { ... }
```
자세한 원리(AOP 프록시로 동작한다는 것 포함)는 [03-영속성-JPA.md](03-영속성-JPA.md)에 따로 정리했다. 요약: 메서드 시작 시 트랜잭션을 열고, 정상 종료 시 커밋, 예외 발생 시 롤백. `readOnly = true`는 조회 전용 메서드에 붙여서 Hibernate가 변경 감지 등 불필요한 작업을 생략하게 하는 최적화 힌트.

## 7. 예외 처리

### `@ExceptionHandler`
`GlobalExceptionHandler.java`:
```java
@ExceptionHandler(ApiErrors.ProjectNotFound.class)
public ResponseEntity<Map<String, String>> handleProjectNotFound(ApiErrors.ProjectNotFound e) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND).body(Map.of("message", e.getMessage()));
}
```
"이 타입의 예외가 컨트롤러 쪽에서 잡히지 않고 위로 던져지면, 이 메서드가 대신 처리해서 응답을 만들어라"는 뜻. 자세한 흐름은 [05-예외처리.md](05-예외처리.md).

## 부록 — 이 프로젝트엔 없지만 자주 보게 될 것들

- `@Autowired`: 필드/세터 주입용. 이 프로젝트는 생성자 주입만 써서 안 쓴다.
- `@Repository`: `JpaRepository`를 상속한 인터페이스는 스프링 데이터 JPA가 **자동으로 구현체를 만들어 빈으로 등록**해주기 때문에 굳이 안 붙여도 된다(스프링 데이터 JPA가 `@EnableJpaRepositories` 스캔 범위 안에서 `Repository` 계열 인터페이스를 찾아 자동 처리).
- `@Component`: `@Service`/`@Controller`/`@Repository`의 "부모" 격. 이 프로젝트에서 직접 쓴 곳은 없다(전부 더 구체적인 걸 씀).
- `@Transactional(propagation = ...)`: 트랜잭션 전파 옵션. 이 프로젝트는 메서드 하나 안에서 트랜잭션이 끝나는 단순한 구조라 propagation을 건드릴 일이 없었다.
